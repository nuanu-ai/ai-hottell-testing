# hottell UI v3

Локальный дашборд AI Hottell. Интерфейс — по пакету дизайна v5.1
(`docs/design/hottell-dashboard-v5.1/`): «Что исправить», Обзор, Сессии, Трение, Инструменты и MCP,
Skills, лента сессии. Показываются только реальные данные выбранных сессий и готовые выводы их
разбора. Чего нет в источниках, показывается как «—»; время — местное, UTC — в подсказке.

```
ui/
  builder/build.py       сборка датасета: сырые сессии Codex + Deep + 13 проверок → local-data/ui/
  builder/telemetry.py   ходы, реплики, вызовы, ошибки, токены, трение, skills
  builder/conclusions.py задания, проверки, выводы и предложения из готовых разборов
  main.go                сервер: страница + /api/dataset, /api/sessions/{id}, /api/rebuild, /api/coach/journal
  coach.go               /api/coach/journal: журнал hottell-coach только на чтение
  main.go                сервер: страница + /api/dataset, /api/sessions/{id}, /api/rebuild, /api/status
  sendstatus.go          статус отправки в сервис команды: hottell status --json раз в минуту

  main.go                сервер: страница + /api/dataset, /api/sessions/{id}, /api/rebuild
  pulse.go               пульс шапки «Живых данных»: /api/pulse из ClickHouse стенда
  static/index.html      интерфейс (без сборки фронтенда)
  CONTRACT.md            формат данных между сборщиком и интерфейсом
```

## Две версии

| Адрес | Версия | Источник |
|---|---|---|
| http://127.0.0.1:8800 | Глубокий разбор | сырые журналы Codex + Deep 2.0 + 13 проверок + реестр предложений (`builder/build.py`) |
| http://127.0.0.1:8801 | Живые данные | только записанные Hooks и нативный OTel из ClickHouse локального стенда (`builder/live.py`), пересборка каждые 5 минут; в шапке — пульс |

Обе версии открываются на «Что исправить» за 7 дней. В живой версии по умолчанию скрыты только явные
служебные задачи Codex (подсказки Desktop и их проверка, память) — кнопка «Все». «Что исправить» начинается
с цикла улучшений (сессии → сигналы → темы → обсуждено → внедрено → проверено), дальше — темы о работе
(гипотезы: у каждой сказано, что проверить до правки), «Исправлено» из журнала коуча и свёрнутые «Здоровье
сбора данных» и «Ограничения данных». Все числа страницы считаются по одной выборке — сессиям под фильтрами;
полнота данных — строкой над темами и KPI, стоимость — наблюдаемая оценка.

Кнопки «Обсудить в Codex / Claude Code» копируют реплику для skill `hottell-coach`
(`$hottell-coach <тема>, период 7 дней`) и показывают команду для терминала; правки из интерфейса
не применяются. Новая сборка датасета подменяется на месте (числа досчитывают, изменённые темы
вспыхивают); скрытая вкладка сервер не опрашивает.

Обе версии поднимает `ui/start-local.sh` (повторный запуск перезапускает). Остановить —
`pkill -f ai-hottell-ui-v3`. Живой версии нужен стенд: `docker compose -f local/docker-compose.yml up -d`.
В живой версии нет строк журнала, поэтому ссылки на события — порядковые номера `#N` внутри сессии;
стоимость Claude Code — его собственная цифра из OTel, у Codex OTel не привязан к сессиям и стоимость — «—».

## Запуск

```sh
python3 ui/builder/build.py          # по умолчанию две тестовые сессии
cd ui && go run . -data ../local-data/ui
# http://127.0.0.1:8800
```

Порты 8787–8790 заняты дашбордами v2, поэтому v3 по умолчанию на 8800. При правке
страницы удобно `go run . -data ../local-data/ui -static static` — страница читается
с диска, без пересборки бинарника.

Сервер слушает только loopback. Датасет и ленты сессий лежат в `local-data/ui/`
(игнорируется Git, права 0600). Кнопка «Обновить» запускает тот же `build.py`
с фиксированными аргументами (принимает запросы только с этой страницы) и подхватывает новую сборку.

Другие сессии: `python3 ui/builder/build.py --ids <id>,<id>`. Сборщик ищет
`~/.codex/sessions/**/rollout-*-<id>.jsonl` и отчёты в `local-data/reports/`.

`GET /api/coach/journal` отдаёт журнал hottell-coach — тот файл, который пишет
`coach_journal` локального MCP `hottell-local`; сервер его только читает. Путь —
флаг `-journal`, по умолчанию `<родитель -data>/coach/journal.jsonl`: для `-data
../local-data/ui` и `../local-data/ui-live` это один и тот же `local-data/coach/journal.jsonl`.
Формат ответа — `CONTRACT.md`, «Журнал коуча».
## Статус отправки

Сервер раз в минуту (и сразу при старте) выполняет `hottell status --json` и отдаёт последний
итог в `GET /api/status`: работает ли отправка в сервис команды. Путь бинаря — флаг `-hottell`,
по умолчанию `~/.local/bin/hottell` (без домашнего каталога — пусто); `-hottell ""` выключает
проверку, и `/api/status` всегда отвечает `unknown`. Одна проверка ограничена 20 секундами, после
срока процесс убивается, а вывод ждётся ещё не больше секунды.

| `state` | Когда |
|---|---|
| `unknown` | проверки ещё не было (или она выключена) |
| `ok` | `hottell status --json` напечатал JSON с `ok: true` (код выхода 0) |
| `problem` | JSON с `ok: false` (код выхода 1), что не так — в `problems` |
| `not_configured` | бинаря нет; не ответил за 20 с; вышел с кодом 1 без вывода — в `reason` первая строка stderr; вывод не JSON (так отвечает старый прототип — бинарь не той версии); в JSON нет `mcp.url` |

`/api/status` отвечает только запросам с loopback, остальным — 403. Ключ MCP и токен коллектора
`hottell status` не печатает, поэтому его вывод отдаётся как есть. Формат ответа — в `CONTRACT.md`.

## Пульс

С флагом `-clickhouse http://127.0.0.1:8123` (база — `-clickhouse-db`, по умолчанию `otel`) сервер отдаёт
`GET /api/pulse`: события хуков за 10 минут по 10 секунд и сессии с событиями за последние 2 минуты.
Первая реплика и проект идущей сессии берутся из `dataset.json`, из ClickHouse — только счёт и время.
Ответ кэшируется на 5 секунд (один запрос к ClickHouse на все вкладки), отвечает только loopback.
Без флага пульса нет (так у :8800): `/api/pulse` — 404, в `/api/meta` — `"pulse": false`, и страница
его не показывает. Страница опрашивает пульс раз в 5 секунд, пока вкладка видна. Формат — в `CONTRACT.md`.

## Что откуда

| Экран | Источник |
|---|---|
| Лента, трение, инструменты, MCP, команды, skills | сырой rollout Codex — восстановленная хронология, не записанные Hooks/OTel |
| Задания, исход, 13 проверок, выводы | Deep 2.0 (`reports/rebuild/<id>/deep.v2.json`), иначе Deep v1 и `reports/coverage/` |
| «Что исправить» | предложения Deep 2.0 и черновые рекомендации Deep v1; эпизоды тестового разбора — как доказательства |
| Стоимость | **оценка** по прайсу API из `dataset.pricing`; фактически Codex работает по подписке |
| «Ваше время» | паузы между ответом агента и вашей следующей репликой, каждая не длиннее 30 минут |

Предложения не применяются из интерфейса: готовность, решение, применение и эффект
показаны отдельно (план 2.0: `docs/plan/hottell-2.0.md` в ветке `codex/hottell-v2`). Решение по теме, внесённое
изменение и итог его проверки записывает skill `hottell-coach` в журнал коуча; «Исправлено» и шаги цикла 4–6
читают его через `/api/coach/journal`. Пока журнала нет, они показывают «—» и «журнал пуст».
