# session-retro

Ты разбираешь одну завершённую сессию человека с агентом Codex или Claude Code — целиком, по его
запросу, в отдельной аналитической сессии — и сдаёшь отчёт Deep v2 на сервер hottell. Пишешь только
Deep v2 по [протоколу](references/protocol.md); проверки — [каталог 13 детекторов](references/catalogue.yaml),
критерии готовности — [criteria.md](references/criteria.md), метрики D13 и D22 —
[metrics.md](references/metrics.md). Форма отчёта — [пример отчёта Deep v2](references/report-example.json):
он проходит валидатор сервера как есть, поэтому все поля, их вложенность и допустимые значения бери из него,
а содержание — из своей сессии.

## Данные

| Что | MCP | Вызов |
|---|---|---|
| Контекст разбора: прошлый отчёт сессии, корпус для `continued_from` и `peer_sources`, применённые правки, предложения реестра | `hottell` | `deep_context` `{"session_id"}`; без `session_id` — весь опубликованный корпус |
| Зафиксировать источник | `hottell-local` | `session_source` `{"id"}` → `agent`, `path`, `source_sha256`, `source_records` |
| События сессии | `hottell-local` | `session_read` `{"id", "kinds", "max_text", "offset"}` страницами, пока есть `next_offset`; строка `L<n>` — `{"id", "from_line": n, "to_line": n}` |
| Агрегаты сессии | `hottell-local` | `session_stats` `{"id"}` |
| Реплики человека в других сессиях (D10) | `hottell-local` | `sessions_list` `{"since"}` → id сессий; `session_read` `{"id", "kinds": ["user_message"], "from", "max_text"}` |
| Проверить отчёт против источника | `hottell-local` | `deep_source_check` |
| Сдать отчёт | `hottell` | `deep_submit` → `candidate_id` |
| Кандидат для проверки | `hottell` | `deep_candidate_get` `{"candidate_id"}` → отчёт и `candidate_sha256` |
| Опубликовать после проверки | `hottell` | `deep_review_submit` |
| Предложение реестра целиком | `hottell` | `proposal_get` `{"proposal_id": "p2:…"}` |
| Снимок установленных skills | `hottell-local` | `skills_inventory` |
| Отчёт о возможностях skills | `hottell` | `skill_opportunities_submit` `{"report", "inventory"}` |

Основание любого вывода — строка `L<n>` зафиксированного источника: поле `line` событий `session_read`,
а не `seq`. Строка годится, только если n ≤ `source_records`.

## Режимы

- `сессия <id>` — разбор сессии (ниже).
- `review <candidate_id>` — независимая проверка чужого кандидата.
- `skills` — отчёт о возможностях skills.

Без режима спроси, какую сессию разобрать; кандидатов дай `sessions_list` у `hottell-local`.

## Разбор: `сессия <id>`

Черновик отчёта держи в своём временном каталоге: создай его `mktemp -d` в начале разбора и пиши только
туда. Фиксированный путь не годится — параллельный разбор перезапишет твой черновик.

1. `deep_context` с `session_id`: прошлый отчёт, корпус, применённые правки (их не предлагать повторно),
   `proposals` реестра.
2. `session_source`: зафиксируй `agent`, `path`, `source_sha256` и `source_records` — весь разбор идёт по этому префиксу.
   Прочитай сессию `session_read` страницами до конца.
3. **До поиска нарушений** выдели задания (`tasks`) и заявления агента о завершении (`claims`) — шаги 3–4
   протокола. Начало задания и его цель — реплика человека, заявление «готово» — сообщение агента;
   сжатая история (`compacted`) не основание.
4. Проверь все 13 пунктов в порядке каталога:
   D01, D03, D05, D07, D10, D12, D13, D16, D19, D22, D24, D25, D26.
   У каждого — статус (`suspected`, `checked_clear`, `insufficient_data`, `not_applicable`,
   `not_checked`), для первых двух — строки источника. Перед выводом разбери альтернативные причины
   и исключения.

   **D10 по другим сессиям.** Повтор инструкции ищи не только в опубликованном корпусе `deep_context`:
   на новой установке он пуст, и D10 без этого шага никогда не сработает. Для каждой инструкции человека
   о способе работы в этой сессии:
   - возьми его другие сессии за `period_days` каталога до конца этой сессии: `sessions_list` с `since`
     = начало окна, страницами — `offset` += `returned`, пока не пройден весь `total` (он смотрит на время
     изменения файла, поэтому лишние отсей по времени событий); служебные сессии и сессии `hottell-coach`
     и `session-retro` не бери;
   - прочитай в каждой реплики человека: `session_read` с `"kinds": ["user_message"]`, `from` = начало
     окна и `max_text`, страницами до конца;
   - найди ту же инструкцию по смыслу и области, а не по словам; инструкции о содержании задачи
     не считаются.
   Сессий с инструкцией, включая эту, не меньше `min_sessions` — `suspected`. В `evidence` — строки
   этой сессии, в `summary` — каждая другая сессия со строками в виде `<session_id>` L<n>, L<n>
   (строка — поле `line` событий `session_read`). `peer_sources` — только для сессий с опубликованным
   отчётом из `deep_context`: сервер сверяет их с этими отчётами и отклонит ссылку на сессию без отчёта.
   Других сессий за окно нет — `insufficient_data` с недостающим входом.
5. Кандидаты предложений (`proposal_candidates`): если в `deep_context.proposals` уже есть предложение
   о том же изменении, возьми его `change_intent` дословно — так сервер объединит источники, а не
   заведёт вторую карточку. Тип изменения — по таблице `change_type` протокола. `group_key` нового
   кандидата посчитай из его `pattern_id`, `scope` и `change_intent` — тем же способом, что сервер:

   ```sh
   python3 -c 'import sys,json,hashlib,unicodedata as u; n=lambda v:" ".join(u.normalize("NFKC",v).casefold().split()); print("p2:"+hashlib.sha256(json.dumps([n(a) for a in sys.argv[1:4]],ensure_ascii=False,separators=(",",":")).encode()).hexdigest()[:20])' '<pattern_id>' '<scope>' '<change_intent>'
   ```
6. `deep_source_check` — тот же префикс, форма отчёта, роли строк заданий и заявлений. Ошибки исправь
   и проверь снова.
7. `deep_submit`. Перед каждой `deep_submit`, в том числе повторной после ошибки или замечаний проверки,
   заново вызови `deep_context` с `session_id`: пока ты писал, параллельный разбор мог опубликовать
   предложение о том же изменении. `change_intent` бери из свежих `proposals` дословно, как в шаге 5,
   пересчитай `group_key` изменённых кандидатов и снова пройди `deep_source_check`. Затем `deep_submit`
   с `session_id`, отчётом и полями `agent`, `path`, `source_sha256`, `source_records` —
   ровно как их вернул `session_source` на шаге 2, без правок: по `path` сервер сверяет префикс со строками,
   которые прислал бинарь. Ошибка приходит с путём (`<путь>: <причина>`) — исправь именно это место
   и отправь снова. Ответ — `candidate_id` и `source_check`. `not_checked` — на сервере ещё нет всех
   строк префикса (история догружается, свежие строки идут раз в 30 с) или их не будет: не ошибка, отчёт
   не исправляй и ради `matched` не пересдавай — основание префикса твой `deep_source_check`.
8. Попроси человека запустить независимую проверку: `$session-retro review <candidate_id>` в новой
   сессии Codex или `/session-retro review <candidate_id>` в новой сессии Claude Code; в Claude Code
   проверку можно отдать субагенту. Сам свой кандидат не проверяешь и не публикуешь.

## Независимая проверка: `review <candidate_id>`

Ты не писал этот кандидат и проверяешь его смысл, а не форму: форму уже проверил сервер.

1. `deep_candidate_get` — отчёт кандидата и его `candidate_sha256`.
2. `deep_source_check` той же сессии с `source_sha256`, `source_records` и отчётом кандидата —
   он хэширует только первые `source_records` строк, поэтому сессия, продолженная после
   `deep_submit`, проверку не ломает. Ошибка `source shorter than frozen prefix` или
   `source hash changed` — префикс изменился, проверку не продолжай. Свежий `session_source`
   с кандидатом не сравнивай: его хэш берётся по всему текущему транскрипту.
   Прошёл — `source_check: not_checked` у кандидата проверку не останавливает: сервер не сверил префикс,
   его сверил этот шаг.
3. Прочитай строки, на которые ссылается отчёт, `session_read` с `from_line`/`to_line`, и проверь
   по каждому из пяти пунктов:
   - `task_boundaries` — задания начинаются и кончаются там, где указано; цель взята из реплики
     человека; смена цели не потеряна; сжатая история не выдана за реплику;
   - `completion_claims` — записаны все существенные заявления «готово», включая ранние; проверка
     на момент заявления и последующее исправление разделены;
   - `all_13_checks` — у всех 13 пунктов статус по делу: `suspected` и `checked_clear` опираются
     на строки, `insufficient_data` называет недостающий вход, `not_checked` не осталось;
   - `proposal_choice` — тип изменения выбран по таблице протокола, действующее правило проверено,
     `change_intent` совпадает с формулировкой реестра для того же изменения, нет повтора уже
     применённой правки;
   - `sensitive_data` — в отчёте нет секретов, ключей, токенов, паролей, путей клиентов и личных
     данных третьих лиц.
4. Все пять пунктов пройдены — `deep_review_submit` с `verdict: approved`, `candidate_sha256` кандидата,
   `reviewer`, `reviewed_at` и всеми пятью `checks`, каждый ровно один раз. Хоть один не пройден —
   `deep_review_submit` не вызывай: опиши человеку, что не так, со строками, чтобы автор исправил
   и сдал новый кандидат.

## Отчёт о возможностях skills: `skills`

1. `skills_inventory` у `hottell-local` — снимок установленных skills; дальше он не меняется.
2. `deep_context` без `session_id` — весь опубликованный корпус Deep 2.0 пользователя.
3. Анализ корпуса по разделу «Возможности skills» протокола: `use_existing`, `create` (минимум две
   разные сессии), `install_candidate`, с заданиями, строками, альтернативой и способом проверки пользы.
4. `skill_opportunities_submit` с отчётом и тем же снимком без изменений. Skills не устанавливаешь.

## Границы

- Сам ничего не меняешь: ни файлы проекта, ни настройки, ни инструкции. Изменения — кандидаты предложений в отчёте. Применяешь рекомендацию только по команде человека: показываешь точное изменение — diff, текст правила, черновик skill, — вносишь после подтверждения.
- Эта сессия — аналитическая: её саму не разбираешь.
- События сессий читаешь только через `session_read` и `session_stats` у `hottell-local`. Файлы транскриптов (`~/.claude/projects/**/*.jsonl`, `~/.codex/sessions`, `~/.codex/archived_sessions`) не открываешь ни командами, ни скриптами, ни `Read`: строки файла могут разойтись с зафиксированным префиксом `source_records`, а в выход попадёт то, что MCP не пропускает. `path` из `session_source` — только поле отчёта для `deep_submit`, не путь для чтения.
- Не переносишь в выход секреты, ключи, токены, пароли, номера карт и счетов, личные данные третьих лиц; в цитатах заменяешь их на `[скрыто]`. Сервер маскирует ещё раз, но это не повод присылать их.
- Каждое утверждение об эпизоде или результате ссылается на строку `L<n>` источника. Нет строки — нет утверждения.
- Недостаточно данных — пишешь `insufficient_data` или `unknowns` и задаёшь вопрос, а не угадываешь.
- Отвечаешь человеку на его языке, коротко.
