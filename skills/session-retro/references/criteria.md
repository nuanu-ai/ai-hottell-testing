# Классы задач и критерии готовности

Критерий готовности — 2–5 проверяемых пунктов, которые делают вердикт `verified` возможным. Проверка засчитывается, только если она относится к пункту критерия: успешная команда или появившийся файл сами по себе цель не подтверждают.

Критерий берётся, по порядку: из постановки (если человек его написал) → из ответа на оранжевый флаг → из шаблона класса ниже, подтверждённого человеком. Шаблон без подтверждения человека — основа для мнения модели, не для вердикта.

Названия конкретных систем в шаблонах — `<в угловых скобках>`: их заполняет участник под свои инструменты.

## Как skill определяет класс

По постановке и первым действиям агента выбирается один `goal_category`. Если в сессии несколько задач, skill размечает сегменты по ходам, каждый со своим классом.

| `goal_category` | Признаки |
|---|---|
| `support_case` | обращение клиента или пользователя, тикет, ответ, решение проблемы |
| `finance_reconcile` | возвраты, возмещения, сверка сумм, выписки, платежи, отчёт по деньгам |
| `admin_process` | документы, письма, регистрации, настройка доступов, оформление, договорённости |
| `research_concept` | исследование, сравнение, концепт, спецификация, презентация по итогам |
| `code_change` | изменение кода в репозитории |
| `other` | не подходит ни один |

## support_case — поддержка

| # | Пункт критерия | Распознаваемая проверка |
|---|---|---|
| 1 | Причина обращения установлена и названа | skill: в финальном сообщении есть причина со ссылкой на данные — лог, запись в `<системе>`, ответ API |
| 2 | Ответ клиенту подготовлен или отправлен по правилам ответа | вызов отправки в `<системе тикетов / мессенджере>` с успешным статусом; или файл ответа создан и не пустой |
| 3 | Тикет в правильном статусе | вызов смены статуса в `<системе тикетов>` с успехом |
| 4 | Если нужна доработка продукта — задача заведена | вызов создания задачи в `<трекере>` с успехом |

Типичные эпизоды: D24 при недоступной системе тикетов, D03 при повторных запросах одного API, D01 — «клиент имел в виду другое».

## finance_reconcile — возвраты и сверка

| # | Пункт критерия | Распознаваемая проверка |
|---|---|---|
| 1 | Итог сходится с контрольной суммой | вывод скрипта или ответа с совпадением итогов; расхождение = 0 или объяснено построчно |
| 2 | Каждое расхождение объяснено | skill: список расхождений с причиной; число объяснённых = числу найденных |
| 3 | Статусы платежей проверены до расчёта | вызов получения статуса платежа предшествует расчёту в той же сессии |
| 4 | Результат оформлен в согласованном формате | файл отчёта создан, не пустой, содержит обязательные поля `<список полей>` |
| 5 | Действия с деньгами не выполнялись без подтверждения человека | нет вызовов изменения платежей без решения человека по разрешению |

Типичные эпизоды: D10 — «сначала статус платежа», D07 и D24 при недоступных выписках, D05 — «отчёт готов» без сходящихся итогов.

## admin_process — административные процессы

| # | Пункт критерия | Распознаваемая проверка |
|---|---|---|
| 1 | Документ или письмо подготовлены по шаблону | файл создан, не пустой, содержит обязательные разделы `<список>` |
| 2 | Отправлено адресату или размещено | вызов отправки или загрузки с успешным статусом |
| 3 | Зафиксирован следующий шаг и ответственный | skill: в финальном сообщении есть следующий шаг, срок, ответственный |

Типичные эпизоды: D01 — неполная постановка, D16 — вопросы по одному, D22 — одинаковые оформления, кандидаты в скрипт.

## research_concept — исследование и концепт

| # | Пункт критерия | Распознаваемая проверка |
|---|---|---|
| 1 | Документ создан в нужном месте и формате | файл создан, не пустой |
| 2 | Утверждения опираются на источники | skill: в документе есть раздел источников; число ссылок ≥ `<N>` |
| 3 | Покрыты вопросы постановки | skill: каждый вопрос из постановки имеет ответ или пометку «не найдено» |
| 4 | Человек принял результат | разметка `outcome ≥ 2`; для `verified` — `outcome = 3` |

Типичные эпизоды: D01 и D10 — формат и глубина, D13 — одна длинная сессия на несколько задач, D12 — компакции.

Работа по одной теме часто идёт в нескольких сессиях и агентах: ресёрч в Codex и Claude, сведение, ревью. Пока сессии не склеиваются в задачу, критерий относится к сессии: у сессии сведения — пункты 1–4, у сессий ресёрча — пункты 2–3.

## code_change — изменение кода

| # | Пункт критерия | Распознаваемая проверка |
|---|---|---|
| 1 | Тесты по изменённой части проходят | команда тестов с кодом 0 после последнего изменения файлов |
| 2 | Изменение ограничено задачей | изменённые файлы относятся к названным в постановке или к их модулю |
| 3 | Изменение сохранено | коммит или PR создан |
