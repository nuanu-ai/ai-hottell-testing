# Метрики и вердикт

Определения для ядра и дашборда. Поля — [model.md](model.md), детекторы — [catalogue.yaml](catalogue.yaml). Период по умолчанию — 7 дней; срез — участник, класс задачи, агент. Аналитические сессии (`kind = analysis`) в метрики не входят.

## 1. Главная метрика — нагрузка на человека

**`human_load_per_verified`** = Σ `human_load_min` по сессиям периода / число сессий с вердиктом `verified`.

- `human_load_min` сессии = `interaction_min` + `rework_min`.
- `interaction_min` — время человека в сессии: `human_active_min`, если агент его отдаёт (Claude Code); иначе число вмешательств × `t_intervention`. Вмешательства — [model.md §3.8](model.md); классы реплик ставит быстрый разбор ([quick-review.md](quick-review.md)), поэтому метрика считается без глубокого разбора.
- `t_intervention` — по умолчанию 1 минута; калибруется по сессиям Claude Code, где есть и активное время, и число вмешательств. Оценочное значение помечается `estimate`.
- `rework_min` — доработка после сессии из разметки человека; нет разметки — `unknown`, не 0. Метрика считается по сессиям с разметкой; рядом — доля размеченных сессий. Сравниваются только периоды с похожей долей (разница не больше 20 п. п.), иначе — «нет данных».
- Вмешательство — не обязательно потеря: ответ на нужный вопрос и уточнение цели — нормальная работа человека. Потери — только подтверждённые эпизоды (§3).

**Условие качества** — показывается рядом, изменение главной метрики засчитывается только при его выполнении: доля `verified` не ниже, чем в сравниваемом периоде, повторных открытий не больше.

Вспомогательные: токены на подтверждённый результат (`tokens_per_verified`), активное время агента на подтверждённый результат, вмешательства на сессию.

## 2. Вердикт

| Вердикт | Правило |
|---|---|
| `verified` | все пункты критерия готовности подтверждены проверками ([criteria.md](criteria.md)) **или** разметка `outcome = 3` / человек принял результат |
| `partial` | часть пунктов подтверждена **или** `outcome = 2` |
| `failed` | проверка пункта провалена, **или** `outcome ∈ {0, 1}`, **или** задача открыта повторно в течение 7 дней |
| `unknown` | нет критерия готовности или проверок по нему и нет разметки |

Разметка человека главнее проверок, если они противоречат; противоречие показывается. Мнение модели (`model_opinion`) и заявление агента (`agent_claim`) хранятся отдельно и на вердикт не влияют. `unknown` открывает оранжевый флаг: вопрос человеку о цели и критерии; ответ пересчитывает вердикт.

Повторное открытие: сессия того же участника и класса в течение 7 дней, в которой skill отметил отсылку к результату предыдущей («опять», «не сработало», «переделай отчёт за август»).

## 3. Затраты эпизода

Считаются по правилу `cost` детектора: токены и минуты участка сессии. Если токены по ходам недоступны, токены участка = токены сессии × доля вызовов участка, пометка `estimate`. Эпизоды, пересекающиеся по ходам, не суммируются: ход относится к эпизоду с наибольшей severity.

`waste_share` сессии = токены подтверждённых эпизодов / токены сессии. Это затраты подозрительных участков, не доказанная экономия.

## 4. Цена контура

За период: токены быстрого разбора ходов и глубокого разбора + минуты человека на разметку (число отметок × `t_label`, по умолчанию 0.5 мин) + минуты на внедрение изменений из журнала. Показывается рядом с изменением главной метрики.

## 5. Прогресс

### 5.1 Сэкономленное время — главное число на обзоре

`saved_min` — оценка времени **человека**, сэкономленного внедрёнными изменениями за период. Главное число на обзоре — только время человека; время агента считается так же, но показывается отдельно и с ним не складывается.

- По каждому изменению из журнала: `saved_min = (m_before − m_after) × n_after`.
- `m_before`, `m_after` — минуты на сессию, которые уходили на паттерн изменения в сессиях того же класса до и после внедрения, по правилу `cost` детектора (§3). Раскладка: **время человека** — вмешательства на участках эпизодов × `t_intervention` плюс доработка, привязанная к паттерну в разметке; **время агента** — длительность участков.
- `n_after` — число сессий класса после внедрения в периоде.
- Засчитывается, только если изменение используется и условие качества выполнено (доля `verified` в классе не ниже); иначе 0 с пояснением.
- Одно изменение за раз в классе задач. Если несколько изменений внедрены в одном классе в одном периоде и влияют на одни и те же эпизоды, эффект общий: показывается один раз на группу изменений и между ними не делится.
- Это наблюдаемая разница, а не доказанная экономия: сложность задач, модель и привычки тоже меняются. Статус — «предварительно», пока нет replay или сопоставимых задач с обеих сторон.
- Меньше 3 сессий с какой-либо стороны — пометка «предварительно». До первых сессий после внедрения не считается.
- Показывается с «≈» и подписью «оценка по N сессиям после внедрения»; раскладка по изменениям — в журнале; цена контура за тот же период (§4) — рядом.

### 5.2 Журнал

- Главная метрика — числом за период с числом сессий `verified`, на которых она посчитана; меньше 3 — «нет данных». График по неделям — после 4 недель данных.
- Изменения из журнала: внедрено; используется — сигнал использования есть хотя бы в одной сессии после внедрения; `verified` / `no_effect` / `worse`.
- Сигнал использования: skill — `SkillUse`; hook — срабатывание в данных сессии; правило в инструкциях — исчезновение повторяющейся инструкции (D10) или связанного паттерна; настройки MCP — вызовы сервера без ошибок.
- Эффект изменения: паттерн и главная метрика в классе задач до и после внедрения, не меньше 3 сессий с каждой стороны; иначе статус `preliminary`.

## 6. Общие цифры

Одна строка в шапке обзора: сессий за период, по агентам, без вердикта.

## 7. Baselines

Общие медианы `human_load_min`, токенов, активного времени, числа вызовов и доля `verified` по классу задачи участника — после ≥ 5 сессий класса. Для D13 в Deep 2.0 единица сравнения — независимое задание или отдельно завершённый запуск автоматизации внутри агрегированного задания: после ≥ 5 сравнимых единиц за 30 дней, даже если они относятся к одному длинному чату. Расход должен быть непересекающимся и привязанным к границам каждой единицы; общую сумму чата не делить поровну. Командный baseline — по share-pack'ам, после ≥ 3 участников.

## 8. Качество детекторов

- `dismissed_share` детектора = dismissed / (confirmed + dismissed) за период.
- Порог детектора пересматривается, если `dismissed_share` > 50 % при ≥ 10 размеченных эпизодах.
- Согласие разборов моделью с человеком: доля совпадений `Review` skill и человека, классов реплик быстрого разбора и исправлений человека; мнению модели о результате доверяют больше при согласии ≥ 0.7.
- Разборы подстраиваются под разметку: подтверждения, снятия и исправления человека подставляются в промпты как примеры. Согласие считается от 10 размеченных сессий, надёжно — от 50; среди размеченных не меньше 30 % отрицательных — снятых эпизодов или исправленных классов.

## 9. Сравнение с командой — после MVP

По share-pack'ам участников, при ≥ 3 участниках. Для каждой практики — значение участника и медиана команды:

| Практика | Определение |
|---|---|
| Сессии со skills | доля сессий с ≥ 1 `SkillUse` |
| Свежесть настроек | доля элементов настроек без статуса `stale` по D26 |
| Неработающие MCP | число серверов с открытым эпизодом D24 |
| Подтверждённые результаты | доля `verified` |
| Нагрузка на человека | `human_load_per_verified` |
| Динамика | изменение нагрузки на человека за 2 недели после внедрённых изменений |

Лучшие практики — участники в верхней четверти по практике, с примерами из их share-pack'ов, если они разрешили цитаты. Объём работы не сравнивается.
