## 1. hottell-coach: разговор об улучшениях в Codex или Claude Code

### Задача

Дашборд не выдаёт готовые советы, а приводит человека в сессию Codex или Claude Code. Там агент со skill `hottell-coach`:
- получает данные через MCP `hottell`;
- объясняет, что мешает;
- вместе с человеком выясняет причину;
- выбирает, что улучшать: опыт работы, инструкции, skill или техническую часть;
- после согласия внедряет изменение.

Skill даёт методологию, MCP — данные и журнал изменений.

### Вход

- **Из дашборда.** В начале «Что исправить» и на каждой карточке находки — кнопки «Обсудить в Codex» и «Обсудить в Claude Code». Кнопка копирует стартовую реплику и показывает команду для терминала:
  - Codex: `$hottell-coach <id находки или тема>, период 7 дней`, в терминале `codex "<реплика>"`;
  - Claude Code: `/hottell-coach <id находки или тема>, период 7 дней`, в терминале `claude "<реплика>"`.
- **Напрямую.** Человек вызывает skill без темы, и skill начинает с обзора.

### Данные: локальный MCP `hottell-local`

В новом бинаре (`temp/cmd/hottell`, hottell v0.2.3) MCP перенесён на сервис команды: имя `hottell` в конфигах агентов занимает удалённый сервер `/mcp` (настройки, токен коллектора, инструкции установки). Локальные инструменты сессий остались только в старом бинаре (`hottell/session_tools.go`).

Коуч работает на данных с машины человека: сырые транскрипты её не покидают и доступны, даже если их отправка выключена. Поэтому в новый бинарь переносится локальный MCP-сервер `hottell-local` (`hottell mcp-local`, stdio) с инструментами `sessions_list`, `session_read` и `session_stats` из старого бинаря. На сервис эти инструменты не переносятся: у человека, выключившего отправку транскриптов, коучу нечего было бы читать.

Два ограничения нужно закрыть:
- `since` и `until` фильтруют по времени изменения файла, поэтому в «последние 7 дней» попадают сессии с репликами из июня. Нужен фильтр по времени самих событий (`from`, `to`) в `session_read` и `session_stats`; skill берёт только события периода.
- `session_read` отдаёт по 100 событий, а `session_stats` по периоду учитывает 20 сессий. Skill дочитывает страницы до `next_offset = 0` и в обзоре называет полноту выборки: сколько сессий и событий просмотрено из найденных.

Добавить два инструмента:
- **`findings`** — находки за период из готовых наборов дашборда:
  - живой набор: `local-data/ui-live/dataset.json` — `findings`, `friction`, `skills`, сессии с `kind`;
  - разобранный: `local-data/ui/dataset.json` и реестр `local-data/reports/v2/proposals.json`.

  Параметры: `since`, `until`, `source: live | reviewed | all`, `id`. Ответ компактный: id, заголовок, вид, готовность, сессии и до 3 доказательств (id сессии плюс номер события или строки). Каталог данных берётся из `HOTTELL_DATA_DIR`, по умолчанию `~/Life/projects/ai-hottell/local-data`.
- **`coach_journal`** — `read` (все записи или по id) и `append` (одна запись). Файл `local-data/coach/journal.jsonl`, права 0600.

Текущие настройки (`AGENTS.md`, `CLAUDE.md`, skills, конфиги MCP, hooks) skill читает с диска сам.

### Методология (ядро SKILL.md)

1. **Начать с журнала.** Для записей с `decision: applied`, у которых наступил `check_after`, найти после внедрения сопоставимые задачи того же агента: тот же класс задач и тот же сигнал.
   - Таких задач нет — `not_enough_data`.
   - Есть — `repeated` или `not_repeated` с числом наблюдений.
   - `not_repeated` означает, что на N задачах повтора не было, а не что изменение доказанно помогло. Так и сказать человеку.
2. **Обзор.** Собрать находки и события за период. Показать до 3 тем, по каждой:
   - что повторяется;
   - 2–3 цитаты с привязкой: id сессии, время и номер события;
   - цена: время человека, токены, повторные просьбы.

   Отдельно назвать полноту выборки. Не предлагать темы, по которым в журнале есть решение `declined` или `not_justified`, если после него не появилось новых оснований. Спросить, с какой темы начать. Если человек пришёл с конкретной темой, сразу перейти к ней.
3. **Причина — вместе с человеком.** Сигнал — повод разобраться, а не доказательство неэффективности человека. Назвать гипотезу и альтернативы. Если подходящее правило или skill уже есть, сначала выяснить, почему не сработало: не попало в контекст, конфликтует с другим правилом или агент его не применил. Задать 1–2 вопроса, ответ на которые знает только человек: намеренно ли так было, чего он ждал, важно ли это. Без его подтверждения причина остаётся гипотезой, и изменение предлагается как проверка, а не как решение.
4. **Выбрать один слой улучшения** и объяснить, почему не соседний. Допустимый исход — «изменение не обосновано»: причина разовая, в окружении или в самом агенте при уже действующем правиле.

   | Основание | Слой | Что меняется |
   |---|---|---|
   | Поведение человека: длинные сессии, долгие паузы, постановка задачи | Опыт | Договорённость; если полезно — шаблон (файл передачи, шаблон постановки) |
   | Устойчивое предпочтение или правило | Инструкции | `~/.codex/AGENTS.md`, `~/.claude/CLAUDE.md`, проектные `AGENTS.md`/`CLAUDE.md` |
   | Повторяемая процедура, требующая суждения | Skill | Правка существующего или новый в `~/.codex/skills`, `~/.claude/skills` |
   | Условие, которое нужно проверять во время работы; операция с определённым входом и выходом; доступ, MCP, разрешения, модель | Техника | Hook, скрипт, конфиг MCP, настройки разрешений и модели |

5. **Показать точное изменение.** Прочитать текущий файл и показать diff или полный текст нового skill. Объяснить, как это будет работать и как откатить.
6. **Внедрить после явного «да».** По одному изменению за раз.
   - Файлы своего агента и другого агента на этой машине правятся прямо в сессии, с согласия человека.
   - Если нужно поле в настройках приложения — дать блок для вставки и сказать, где это поле.
7. **Записать в журнал** через `coach_journal.append` любое решение по теме: `applied`, `declined`, `not_justified` или `test`. Одна запись — одно изменение одной цели.

### Правила (в SKILL.md дословно)

- Не дублировать. Если правило уже есть в настройках, но нарушается, уточнять существующее (файл и строка), а не добавлять второе.
- Сначала поправить существующий skill, потом создавать новый. Имя нового — по классу задач, а не по сегодняшней задаче.
- Не превращать в правило: сбои окружения (это починка), утверждения «инструмент X не работает», разовые ошибки, разовые задачи, способы, которые так и не сработали.
- Предпочтение, относящееся к задаче, у которой есть skill, — в этот skill; общее — в инструкции. Никогда в оба места.
- Без цитат из сессий темы нет.
- Без явного согласия человека ничего не менять.
- Секреты, пути клиентов и имена третьих лиц маскируются везде: в цитатах, в изменениях и в журнале. В журнал попадают ссылки на события и цитата не длиннее 200 символов.

### Запись журнала

```json
{
  "id": "20261001T060000-k3f9",
  "topic_key": "scope-creep-engineering",
  "at": "2026-10-01T06:00:00Z",
  "agent": "codex | claude",
  "topic": "Одной фразой",
  "findings": ["<id>"],
  "evidence": [{"session": "<id>", "at": "2026-09-30T08:14:02Z", "seq": 412, "quote": "до 200 символов, маскировано"}],
  "decision": "applied | declined | not_justified | test",
  "layer": "experience | instructions | skill | technical | null",
  "target": "~/.codex/AGENTS.md",
  "before_sha256": "…",
  "after_sha256": "…",
  "change": "Кратко, что изменено",
  "rollback": "Как откатить",
  "check": "Класс задач и сигнал, по которым проверять",
  "check_after": "2026-10-08",
  "result": "repeated | not_repeated | not_enough_data | null",
  "observations": null
}
```

`id` уникален для каждой записи. `topic_key` — устойчивый ключ темы: по нему skill не предлагает повторно отклонённые темы и связывает проверки с исходным изменением.

### Изменения в проекте

- **`analytics/coach/SKILL.md`** — frontmatter `name: hottell-coach` и `description` с триггером; методология и правила. Установка — симлинки в `~/.codex/skills/hottell-coach` и `~/.claude/skills/hottell-coach`, команда в `README.md`.
- **Бинарь `temp/cmd/hottell`** — локальный MCP `hottell-local`: перенос инструментов сессий из `hottell/session_tools.go`, регистрация в конфигах обоих агентов командой `hottell install`, фильтр по времени событий (`from`, `to`) в `session_read` и `session_stats`; инструменты `findings` и `coach_journal`. Тесты: события вне периода не возвращаются; чтение обоих наборов; отсутствие файлов; запись журнала (права 0600, одна строка JSON на запись).
- **`ui/`** — кнопки «Обсудить в Codex» и «Обсудить в Claude Code»: копирование реплики, показ команды для терминала. Раздел «Исправлено» читает журнал через `GET /api/coach/journal`: изменение, слой, дата, итог проверки с числом наблюдений. `not_repeated` подписан как «повтора не было на N задачах». Вид и расположение элементов — по `2026-10-01-ux.spec.md`.

### Приёмка

Сначала skill и MCP, без интерфейса. Skill проходит пять случаев на реальных данных:
1. **Правило уже есть.** Тема «просьба не раздувать реализацию» (4 сессии): skill находит действующее правило в настройках и разбирает, почему оно не сработало. Допустимые исходы — уточнить существующее правило или «изменение не обосновано». Добавить второе правило — провал.
2. **Сбой окружения.** Ошибки из-за отсутствующей программы или настройки: skill предлагает починку, а не правило.
3. **Полезная повторяемая процедура.** Skill предлагает правку существующего skill или новый skill уровня класса задач, с тестовым примером из сессии.
4. **Нет сопоставимых задач после изменения.** Проверка журнала даёт `not_enough_data`.
5. **Граница периода.** Событие старше периода из недавно изменённого файла в обзор не попадает; обзор называет полноту выборки.

Затем интерфейс:
- по кнопке из дашборда skill в Codex и в Claude Code проходит цикл: тема с привязанными цитатами → вопрос о причине → одно изменение с diff или «не обосновано» → запись в журнал;
- отклонённая тема без новых оснований не предлагается снова;
- «Исправлено» показывает записи с итогом и числом наблюдений.

## 2. Живой дашборд: исправления

### 2.1 Ложная метка «записан только хвост»

- `ui/builder/live.py:696–697`: `partial` выставляется при любом `SessionStart` с `source == "resume"`, даже если сессия записана с первого события. Codex Desktop и Claude Code присылают `resume` при возврате к сессии.
- Пример: 01a0f57b создана в 03:22:03, первое событие в 03:22:08, `SessionStart` ×2 — сессия помечена как начатая до подключения хуков. Так же помечены 01a0f2bf и 6d2750fc. Из-за этого занижается строка «Полнота данных».
- Правка: `resume` даёт `partial`, только если перед ним нет `SessionStart` с `source == "startup"`. Проверку uuid7 `first_hook − created > PARTIAL_AFTER_H` сохранить.
- Тесты: startup → вызовы → resume даёт `recorded`; resume без startup даёт `partial`.

### 2.2 Короткие ID совпадают

- `live.py:922` (`"short": sid[:8]`), тексты в `live.py:1244, 1460, 1467` и `short()` в `index.html:419` берут первые 8 знаков. У uuid7 они меняются примерно раз в 65 с: в данных дважды встречаются 01a0f11d, 01a0f57b и 01a0f57c.
- Правка: короткий ID = первые 8 и последние 4 знака (`01a0f57b…4b74`) — везде одинаково.

### 2.3 Стартовая вкладка

`index.html:703` `defaultView()` открывает Skills, если использован хоть один skill. По умолчанию нужно «Что исправить».

### 2.4 Длительность в списке сессий

Колонка «Длит.» показывает `wall_min` — сколько сессия была открыта (01a0f058: 23 ч 42 м при 614 мин работы). В колонке должно быть `active_min`, `wall_min` — в подсказке.

### 2.5 Запуски по расписанию в итогах

Сессии `kind == "automation"` попадают в KPI «Агент работал» и «Ваше время»: у 019fcbc7 это 7 ч. Исключать их из «Агент работал» и «Ваше время» и показывать под KPI отдельной строкой «ещё N ч — запуски по расписанию».

- В браузере на :8801:
  - 01a0f57b не помечена как частичная;

## 3. Связка с сервисом команды

Отправку в общий контур уже закрывает сервис команды (`temp/`, снимок `harness-telemetry`):
- пользователи и приглашения;
- вход по паролю и passkey;
- ключ MCP и токен коллектора на странице «Подключение»;
- приём OTLP;
- страница «Что отправлять» с семью видами запретов: агент, источник, событие хука, поле события, папка, содержимое нативного OTel, догрузка истории.

Ручной пакет для хаба не делать. Добавить только статус отправки в дашборд.

- `ui/main.go`: раз в минуту выполнять `hottell status --json` и отдавать результат через `GET /api/status`, только loopback.
- В шапке дашборда одна строка. Если отправка работает: «Отправка: работает · последняя 2 мин назад · в очереди 0 · настройки v7 · Что отправлять →». Если есть проблемы — первая из `problems` цветом предупреждения. Нет бинаря или подключения — «Отправка не настроена · Подключение →».
- Ссылки ведут на страницы сервиса `/telemetry` и `/connect`. Адрес сервиса берётся из `mcp.url` в статусе.

Приёмка: строка совпадает с `hottell status --json` в трёх состояниях — бинаря нет, подключено, последняя отправка с ошибкой.

## Не делать в этой итерации

- Изменения без явного согласия человека в сессии.
- Фоновый или плановый запуск коуча.
- Автоматическое отслеживание вставки по маркерам и уборку устаревших правил.
- Ручной пакет для хаба: отправку закрывает сервис команды.

## Открыто

- **Выбор отдельных сессий.** В сервисе отправку можно запретить только для папки; выбрать конкретные сессии нельзя. Решить, достаточно ли папок, или нужен вид запрета «Сессия». Он работал бы для продолжающихся сессий; уже отправленные данные понадобилось бы удалять.
- **Персонализация Codex.** Инструкции Codex по умолчанию правятся в `~/.codex/AGENTS.md`. Если у человека персонализация Codex задана в поле настроек приложения, skill не правит файл, а даёт блок для вставки в это поле.
