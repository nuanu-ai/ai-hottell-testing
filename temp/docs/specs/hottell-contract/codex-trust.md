# Доверие к хукам Codex без `/hooks`

Задача HT-77, эпик HT-76. Проверено на codex-cli 0.159.0 (`rust-v0.159.0`), macOS arm64,
2026-10-01.

## Итог

**Работает.** Если бинарь сам записывает в `config.toml` доверие с вычисленным хэшем,
хук Codex срабатывает без `/hooks`. Запасной путь из HT-68 (просить пользователя сделать
`/hooks`) не нужен, пока Codex не поменяет алгоритм.

Реализация — `internal/hottell/codextrust`: `Key` строит ключ состояния, `Hash` — хэш.

## Как Codex решает, запускать ли хук

Источник — `codex-rs/hooks/src/engine/discovery.rs` (`append_matcher_groups`, `hook_hash`,
`hook_trust_status`), `codex-rs/hooks/src/lib.rs` (`hook_key`),
`codex-rs/config/src/fingerprint.rs` (`version_for_toml`).

Хук из пользовательского слоя (`$CODEX_HOME/hooks.json` или `[hooks]` в
`$CODEX_HOME/config.toml`) запускается, только когда он включён и его статус `Trusted`:
в `config.toml` есть таблица состояния с `trusted_hash`, равным текущему хэшу хука.
Нет записи — статус `Untrusted`; хэш не совпал — `Modified`. В обоих случаях хук молча
пропускается, `codex exec` ничего об этом не пишет. Управляемые хуки (MDM, system,
облачные требования) доверия не требуют. Хуки включены по умолчанию (`[features] hooks`,
стадия Stable).

### Ключ

```toml
[hooks.state."<источник>:<событие>:<группа>:<обработчик>"]
trusted_hash = "sha256:<hex>"
```

- `<источник>` — абсолютный путь файла, откуда загружен хук, как его строит Codex:
  `$CODEX_HOME/hooks.json` или `$CODEX_HOME/config.toml`.
- `<событие>` — метка события в snake_case: `pre_tool_use`, `permission_request`,
  `post_tool_use`, `pre_compact`, `post_compact`, `session_start`, `session_end`,
  `user_prompt_submit`, `subagent_start`, `subagent_stop`, `stop`, `interrupt`.
- `<группа>` — индекс группы-матчера в массиве события, с нуля, в порядке файла.
- `<обработчик>` — индекс обработчика в массиве `hooks` группы, с нуля.

Ключ зависит от позиции, а не от содержимого.

### Хэш

`"sha256:" + hex(sha256(канонический JSON нормализованной идентичности))`.

Идентичность — объект:

| поле | значение |
| --- | --- |
| `event_name` | метка события в snake_case, как в ключе |
| `matcher` | матчер группы; поля нет, если матчера нет или событие его не использует (`UserPromptSubmit`, `Stop`, `Interrupt`) |
| `hooks` | массив из одного нормализованного обработчика |

Нормализованный обработчик команды:

| поле | значение |
| --- | --- |
| `type` | `"command"` |
| `command` | команда как в файле |
| `timeout` | всегда присутствует: заданный или 600, не меньше 1; для `SessionEnd` и `Interrupt` — заданный или 1, в пределах 1…3 |
| `async` | всегда присутствует, как в файле (по умолчанию `false`) |
| `statusMessage` | только если задан |
| `additionalContextLimit` | только если задан, не равен 2500 и событие — `PreToolUse`, `PostToolUse`, `SessionStart`, `UserPromptSubmit` или `SubagentStart` |

`commandWindows` в идентичность не входит.

Канонический JSON — как `serde_json::to_vec`: без пробелов, ключи объектов отсортированы
по байтам, числа целые. Строки экранируются только в `"`, `\` и управляющих символах
(`\b \f \n \r \t`, остальные `\u00xx`); `<`, `>`, `&`, U+2028, U+2029 и не-ASCII остаются
как есть. Поэтому в Go используется свой сериализатор, а не `encoding/json`: тот
экранирует `<`, `>`, `&`, U+2028 и U+2029.

Одинаковые хуки из `hooks.json` и `config.toml` дают один и тот же хэш: различается только
ключ.

## Проверка

### Эталон из локального конфига

Функция проверена на всех 20 записях `[hooks.state]` локального `~/.codex/config.toml`,
чьи хуки лежат в `~/.codex/hooks.json`. Файлы только читались, их SHA-256 до и после
совпали; сравнивались только хэши, значения из конфига не публиковались.

- 10 записей совпали с хэшем текущих хуков.
- 10 записей не совпали. Перебор показал: они вычисляются тем же алгоритмом из той же
  команды с `async: true`, а в текущем `hooks.json` поля `async` нет. Доверие записано
  до того, как хук поменяли, и сейчас эти хуки для Codex `Modified` — не запускаются.

Итого все 20 хэшей, записанных самим Codex, воспроизведены алгоритмом.

### Живая проверка

Временный `CODEX_HOME` в каталоге для черновиков, настоящий `~/.codex` не менялся.
Запуск: `codex exec --skip-git-repo-check -s read-only "Reply with the single word OK."`
из пустого каталога. Хук `UserPromptSubmit` дописывает строку в файл-маркер. Хэш и ключ
вычислены `codextrust`.

| прогон | `hooks.json` | доверие в `config.toml` | маркер |
| --- | --- | --- | --- |
| 1 | наша группа | нет | не записан — хук не сработал |
| 2 | наша группа | вычисленный хэш на `:0:0` | записан — хук сработал |
| 2b | наша группа | хэш с одной изменённой цифрой | не записан |
| 3 | чужая группа, затем наша | вычисленный хэш на `:0:0` | не записан: наш хук переехал на `:1:0` |
| 3b | чужая группа, затем наша | вычисленный хэш на `:1:0` | записан |
| 4 | наша группа, затем чужая | вычисленный хэш на `:0:0` | записан |
| 5 | только чужая группа; наша — в `[hooks]` `config.toml` | вычисленный хэш на `<config.toml>:user_prompt_submit:0:0` | записан; Codex предупреждает `loading hooks from both … prefer a single representation for this layer` |
| 6 | четыре события, см. ниже | вычисленные хэши | записаны все четыре |

В прогоне 6 проверены поля идентичности: `SessionStart` с матчером, `timeout: 30` и
`statusMessage` с `<`, `&`, `"`; `Stop` с `async: true`, матчером и
`additionalContextLimit` (оба Codex отбрасывает); `SessionEnd` с `timeout: 9`
(обрезается до 3); `UserPromptSubmit` без полей. Эти хэши — эталоны теста
`TestHashMatchesCodex`. В прогоне 2 Codex сам `config.toml` не переписал.

## Ограничения и как их обойти

- **Позиция.** Ключ содержит индексы группы и обработчика. Если пользователь или другой
  инструмент вставит группу перед нашей в том же событии, старая запись доверия указывает
  на чужой хук (у него другой хэш — `Modified`), а наш хук становится `Untrusted`. Чужие
  группы после нашей не мешают (прогоны 3 и 4).
  Решение для HT-94: при каждой установке и применении настроек бинарь находит свои
  обработчики по команде, пересчитывает для каждого ключ и хэш и перезаписывает свои
  записи `[hooks.state]` (прогон 3b). Новую группу бинарь ставит последней в событии, а
  уже стоящую свою группу обновляет на её месте (HT-94). Первой её не ставим: вставка
  перед чужими группами сдвинула бы их ключи, и Codex молча перестал бы запускать хуки
  пользователя до `/hooks`, а переносить чужое доверие бинарь не вправе — он правит
  только свои записи. Записи доверия, которые после сдвига указывают на чужие хуки,
  бинарь не трогает: он правит только ключи, где сейчас стоят его обработчики.
- **Отдельный файл.** Хуки можно держать в `[hooks]` `config.toml` (прогон 5): тогда
  правки `hooks.json` их ключи не сдвигают. Но Codex на каждый запуск печатает
  предупреждение о двух представлениях, если в слое заняты оба; позиционная зависимость
  внутри `config.toml` остаётся. Основной путь — `hooks.json` с пересчётом доверия.
- **Любое изменение хука** — команды, таймаута, `async`, матчера, `statusMessage` —
  меняет хэш. Бинарь пересчитывает доверие при каждой записи своих хуков.
- **Путь источника** берётся тем, каким его строит Codex из `CODEX_HOME` (или
  `~/.codex`); бинарь использует тот же путь. Как Codex обходится с символическими
  ссылками в пути, не проверялось.
- **Версия Codex.** Алгоритм не является публичным контрактом Codex. Если после
  обновления Codex хук перестал срабатывать, запасной путь — HT-68: инструмент установки
  просит пользователя сделать `/hooks`.
- Реализованы только обработчики `type: "command"`; `mcp_tool` бинарю не нужен.
