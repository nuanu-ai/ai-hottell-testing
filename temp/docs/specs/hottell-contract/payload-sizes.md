# Размеры событий хуков и строк транскриптов при больших выводах

Эксперимент HT-79 (эпик HT-76). Цель — узнать реальные размеры данных, которые
`hottell` получает от агентов, чтобы хук читал stdin целиком, а лимиты приёма
(HT-57) не отвергали обычные записи.

Дата: 2026-10-01. Версии: Claude Code 2.1.285, Codex CLI 0.159.0, macOS arm64.

## Как измеряли

- Оба агента запускались в headless-режиме (`claude -p`, `codex exec`) с
  временными каталогами конфигурации (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`).
  Настоящие `~/.claude` и `~/.codex` не менялись.
- Временный хук на `PostToolUse` (у Claude ещё `PostToolUseFailure`) читал
  stdin целиком и записывал только размеры: весь stdin и `tool_response`
  в JSON-сериализации.
- Данные синтетические: файлы из повторяющейся строки `lorem ipsum …`
  на 5 МиБ и 20 МиБ и вывод `seq 1 4845000` (≈ 50 МиБ).
- Транскрипты разбирались после прогона: размер строки JSONL, размер
  результата инструмента, маркеры обрезки, файлы в `tool-results/`.

Размеры указаны в байтах.

Выводы:

- `tool_response` в хуке совпадает с `toolUseResult` транскрипта.
- Вывод Bash больше ≈ 30 000 символов Claude выносит в
  `<каталог проекта>/<session-id>/tool-results/<id>.txt`. В хук и в JSONL
  попадает только превью и путь к файлу. Полный вывод есть только в этом файле.
- Read ограничен до выполнения: файл больше 256 КБ целиком не читается,
  один вызов возвращает не больше 25 000 токенов. Отказ приходит событием
  `PostToolUseFailure` размером около 1 КБ.
- **Наибольшее наблюдённое событие хука Claude — 101 821 байт**
  (`PostToolUse` Read). Наибольшая строка транскрипта — 209 882 байта.

## Codex

У Codex нет отдельного инструмента чтения файла: «прочитать файл» модель
выполнила через `exec_command` с `cat`. В хуке `tool_name` — `Bash`.

Выводы:

- `tool_response` в хуке Codex — тот же текст, что модель получает в
  `function_call_output`. Он обрезан по `max_output_tokens`, который выбирает
  модель, и по внутреннему потолку около 10 000 токенов (≈ 40 КБ).
- Codex сам хранит не больше 1 МиБ вывода команды: `stdout` и
  `aggregated_output` в `item_completed` обрезаны до 1 048 576 байт плюс
  маркер. Остальное теряется, отдельного файла нет.
- Строка `item_completed` содержит вывод дважды (`stdout` и
  `aggregated_output`) плюс `formatted_output`, поэтому одна строка транскрипта
  доходит до ≈ 2,4 МБ. При непустом `stderr` расчётный потолок — около 3,2 МБ.
- **Наибольшее наблюдённое событие хука Codex — 41 498 байт.** Наибольшая
  строка транскрипта — 2 410 724 байта.

## Сводка

| Агент | Наибольшее событие хука | Наибольшая строка транскрипта | Где полный вывод |
|---|---:|---:|---|
| Claude Code | 101 821 | 209 882 | `tool-results/<id>.txt` рядом с транскриптом, без ограничения размера |
| Codex | 41 498 | 2 410 724 | нигде: только первые 1 МиБ в rollout |

Хуки не получают многомегабайтных выводов ни у одного агента: оба агента
обрезают вывод до вызова хука. Многомегабайтными бывают строки транскрипта
Codex.

Не измерялось: `Write` и `Edit` с большим содержимым в `tool_input`, выводы
MCP-инструментов, изображения. Их размер ограничен только самим агентом,
поэтому хук всё равно читает stdin до конца, без своего лимита.

## Рекомендация для HT-57

- **Одна запись — не больше 8 МиБ** в закодированном OTLP-виде без сжатия.
  Наибольшая наблюдённая запись — строка транскрипта Codex ≈ 2,4 МБ, расчётный
  потолок ≈ 3,2 МБ. При передаче строки транскрипта как строкового `body` в
  OTLP/JSON экранирование увеличивает её примерно до двух раз, до ≈ 6,4 МБ.
  8 МиБ покрывают это с запасом.
- **Один запрос — не больше 16 МиБ** после распаковки gzip. Так запрос вмещает
  хотя бы одну запись предельного размера, а бинарь собирает пачки по размеру
  ниже этого порога.
- Запись больше 8 МиБ сервер отвечает 413, бинарь переносит её в папку
  отклонённых по таблице ответов HT-57. По этим измерениям такие записи
  на практике не возникают.
- Хук (`hottell hook`) читает stdin целиком, без лимита. Наблюдённые события
  не превышают 102 КБ.
