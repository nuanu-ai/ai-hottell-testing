# Контракт hottell: приём записей хуков и транскриптов

Задачи HT-53 и HT-57, эпик HT-51. Документ задаёт, в каком виде бинарь
`hottell` отправляет события хуков и строки транскриптов в приём `/v1/*`
и как приём с ними обращается. По нему строятся бинарь, приём OTLP
(HT-72) и проставление пользователя на приёме (HT-74).

Раздел «Записи» — форма одной записи (HT-53). Раздел «Приём» — endpoint,
лимиты, ответы сервера с реакцией бинаря и таблица связки ключей между
источниками (HT-57).

Имена событий, полей и форматы транскриптов взяты из отчётов исследования
HT-50: «Claude Code 2.1.285 — хуки, OTel, транскрипты» и «Codex 0.159.0 —
хуки, OTel, транскрипты». Размеры записей — из `payload-sizes.md` (HT-79).
Какие данные бинарь вообще не отправляет, задаёт `settings.md` (HT-52).

## Записи

### Общая форма

- Бинарь отправляет события хуков и строки транскриптов **OTLP-логами**
  в тот же приём, что и нативный OTel агентов. Одна запись — одна
  `LogRecord`.
- **Запись лежит целиком в теле** `LogRecord.body`: без раскладки на поля
  и без обрезки. Атрибуты записи — копии ключей из тела и сведения
  о происхождении записи (аргумент `hottell hook`, путь файла, состояние
  бинаря), нужные серверу для отбора, связки и отбрасывания повторов.
  Источник правды о содержимом — тело.
- Имена атрибутов, скопированных из тела, повторяют имена полей агента
  (`cwd`, `prompt_id`, `tool_use_id`, `turn_id`). Исключение — `session.id`:
  так же называется атрибут нативного OTel Claude. Атрибуты, которых
  в теле нет, получают префикс по виду записи (`hook.`, `transcript.`),
  кроме общих `agent` и `backfill`.
- Тело — `stringValue` с исходным текстом записи. Если исходные байты
  не являются корректным UTF-8, тело уходит как `bytesValue` с теми же
  байтами без изменений (в JSON-кодировке OTLP — base64).
- Записи хуков и записи транскриптов уходят в разных `ResourceLogs`
  (у них разный `service.name`). В одном `ResourceLogs` могут лежать записи
  обоих агентов: агент указан атрибутом записи.
- `InstrumentationScope`: `name` = `hottell`, `version` = версия бинаря.
  Сервер на scope не опирается.
- `severityNumber` и `severityText` бинарь не заполняет. `traceId`
  и `spanId` пустые.
- Атрибуты, которых нет в таблицах ниже, бинарь не отправляет. Сервер
  хранит пришедшие атрибуты как есть и не отвергает запись из-за лишнего
  атрибута.

Обязательность в таблицах:

- **да** — бинарь отправляет у каждой корректной записи. Исключение —
  повреждённое событие хука (см. «Событие хука»): оно уходит без
  атрибутов, которые из него не извлечь, и сервер принимает его так же;
- **если есть** — бинарь отправляет, когда значение есть в исходной
  записи; иначе атрибута нет совсем (не пустая строка и не `null`);
- **нет** — клиент не отправляет, поле проставляет сервер.

Типы — типы `AnyValue` OTLP: `string` — `stringValue`, `int` —
`intValue` (int64; в JSON-кодировке OTLP — десятичная строка), `bool` —
`boolValue`.

### Ресурс

| Атрибут | Тип | Обязательность | Значение |
|---|---|---|---|
| `service.name` | string | да | `hottell-hooks` — для событий хуков; `hottell-transcripts` — для строк транскриптов, в том числе истории |
| `service.version` | string | да | версия бинаря — то, что печатает `hottell version` (например, `0.1.0` или `dev+<commit>`) |
| `host.name` | string | да | имя машины — результат `os.Hostname()` на Mac |
| `hottell.user.id` | string | нет | id пользователя (UUID в нижнем регистре). **Проставляет только сервер** по токену коллектора; значение от клиента сервер удаляет и записывает своё |

`service.name` бинаря не совпадает с нативными `claude-code`,
`claude-code-desktop`, `codex_exec`, `codex-app-server` и другими
`codex_*`: по нему записи hottell отделяются от нативного OTel агентов.

### Событие хука

Одна запись — одно событие, которое `hottell hook claude|codex` получил
на stdin и которое прошло запреты агента, источника `hooks`, папки
и события (`settings.md`, «Порядок применения», шаги 1–4).

**Тело** — JSON события строкой:

- если запрещённых полей нет — stdin байт в байт, без изменений;
- если есть запрещённые поля (`hook_fields.denied`, шаг 5) — тот же
  JSON-объект без этих полей верхнего уровня, сериализованный заново;
  порядок ключей и пробелы могут отличаться от исходных, остальные
  значения не меняются: значения верхнего уровня переносятся исходными
  байтами JSON, без перекодирования чисел и экранирования HTML-символов.

**Атрибуты записи.** Значения берутся из полей верхнего уровня тела,
которое уходит (после вырезания запрещённых полей). Поле со значением
`null` или не строкой считается отсутствующим.

**Повреждённое событие.** У корректного события агента обязательные поля
есть всегда: схемы событий обоих агентов их требуют. Если stdin —
не JSON-объект или в нём нет строковых `session_id`, `hook_event_name`
или `cwd`, бинарь всё равно отправляет запись: тело — stdin байт в байт,
из атрибутов — `agent` и те, что удалось извлечь. Запреты события,
папки и полей к такой записи не применяются, потому что их не к чему
применить; запреты агента и источника `hooks` применяются.

| Атрибут | Тип | Обязательность | Откуда |
|---|---|---|---|
| `agent` | string | да | `claude` или `codex` — аргумент `hottell hook` |
| `hook.event_name` | string | да | поле `hook_event_name`, например `PostToolUse` |
| `session.id` | string | да | поле `session_id` |
| `cwd` | string | да | поле `cwd` |
| `prompt_id` | string | если есть | поле `prompt_id`. Есть только у Claude, и то не до первого промпта сессии |
| `tool_use_id` | string | если есть | поле `tool_use_id`. Есть у tool-событий обоих агентов, кроме `PermissionRequest` |
| `turn_id` | string | если есть | поле `turn_id`. У Codex — во всех событиях, кроме `SessionStart` и `SessionEnd`; у Claude — в `MessageDisplay` |

`session_id`, `hook_event_name` и `cwd` запретить нельзя (`settings.md`,
вид 4), поэтому обязательные атрибуты есть всегда. Ключи связки
(`prompt_id`, `tool_use_id`, `turn_id`) запретить можно: запрещённое поле
не уходит ни в теле, ни в атрибуте.

Время события — поле записи `timeUnixNano`, отдельного атрибута нет
(см. «Время»).

### Строка транскрипта

Одна запись — одна строка JSONL-файла транскрипта, прошедшего запреты
агента, источника `transcripts` и папки (`settings.md`, шаги 1–3).

**Тело** — строка целиком, без завершающего перевода строки (`\n`,
а также `\r` перед ним). Бинарь отправляет только законченные строки:
хвост файла без `\n` ждёт, пока агент допишет строку.

**Какие файлы.** Корень агента — каталог, относительно которого
указывается путь:

| Агент | Корень | Основной транскрипт | Транскрипт субагента |
|---|---|---|---|
| `claude` | `~/.claude/projects` (при `CLAUDE_CONFIG_DIR` — `$CLAUDE_CONFIG_DIR/projects`) | `<project>/<session-id>.jsonl` | `<project>/<session-id>/subagents/agent-<id>.jsonl` |
| `codex` | `~/.codex` (при `CODEX_HOME` — `$CODEX_HOME`) | `sessions/YYYY/MM/DD/rollout-<время>-<thread-id>.jsonl` и то же в `archived_sessions/`, в том числе `.jsonl.zst` | тот же вид файла; субагент отличается содержимым первой строки |

- **`.jsonl.zst`** бинарь распаковывает сам. По сети уходит распакованная
  строка, в теле нет следов сжатия. Нумерация строк — по распакованному
  содержимому, поэтому она не меняется, когда Codex сжимает старый файл.
- **Rollout субагента Codex** начинается с копии истории родителя. Бинарь
  эту копию не отправляет (HT-89): уходят первая строка (`session_meta`
  самого субагента) и собственные записи субагента. Граница — поле
  `session_meta.payload.subagent_history_start_ordinal`: Codex 0.159.0
  пишет `session_meta` субагента с `ordinal` 0, копию записей родителя —
  с `ordinal` от 1 до N, а в поле кладёт N+1
  (`LiveThread::create_with_inherited_model_context` в
  `codex-rs/thread-store`); строки после первой с `ordinal` меньше этого
  значения — копия. Так же их пропускает сам Codex, когда строит историю
  субагента. Rollout без этого поля, в том числе старого формата без
  `ordinal`, отправляется целиком. Номера `transcript.line` остаются
  номерами строк в файле, поэтому у субагента после первой строки они
  начинаются не с 2.
- `tool-results/`, `*.meta.json` и другие файлы рядом с транскриптами
  не отправляются: это не строки транскрипта.

**Атрибуты записи:**

| Атрибут | Тип | Обязательность | Значение |
|---|---|---|---|
| `agent` | string | да | `claude` или `codex` |
| `session.id` | string | да | id сессии, с которым совпадает `session_id` хуков. Claude: `<session-id>` из пути — имя основного файла или каталог над `subagents/`; у субагента это id родительской сессии. Codex: `<thread-id>` из имени rollout-файла; у субагента это id его собственного треда, id родителя есть только в теле первой строки (`session_meta.payload.parent_thread_id`). `<thread-id>` — последние 36 символов имени файла без `.jsonl` и `.zst` |
| `transcript.kind` | string | да | `main` — основной транскрипт; `subagent` — транскрипт субагента. Claude: файл лежит в `subagents/`. Codex: в первой строке (`session_meta`) `payload.thread_source` = `subagent` |
| `transcript.path` | string | да | путь файла относительно корня агента, разделитель `/`, как файл называется на диске сейчас (с `.zst`, если файл сжат), например `sessions/2026/09/21/rollout-…-<thread-id>.jsonl.zst` |
| `transcript.line` | int | да | номер строки в файле, начиная с 1, по распакованному содержимому |
| `backfill` | bool | да | `true` — строка из истории (см. ниже); `false` — строка, дописанная после начала слежения |

**Позиция строки и повторы.** Ключ строки — (`hottell.user.id`, `agent`,
`session.id`, имя файла, `transcript.line`), где имя файла — последний
сегмент `transcript.path` без суффикса `.zst`. Сервер хранит первую
принятую запись с таким ключом, остальные отбрасывает. Каталог в ключ
не входит: Codex переносит rollout из `sessions/` в `archived_sessions/`
и сжимает старые файлы, а имя файла и номера строк при этом остаются
прежними. Бинарь может отправить строку повторно (повтор после сбоя,
перезапуск, одна и та же строка из истории и живого слежения) — это
не ошибка.

Транскрипт считается дописываемым в конец. Если файл стал короче, чем
уже отправленная часть (перезапись, rewind), бинарь новые строки с уже
отправленными номерами не отправляет — сервер всё равно отбросил бы их
как повторы. Такая потеря допустима: агенты пишут транскрипты
дозаписью, перезапись — редкий случай.

**История (`backfill`).** При первом запуске фонового процесса бинарь
запоминает число законченных строк в каждом транскрипте, который в этот
момент есть у агента. Эти строки — история: они уходят с `backfill` = `true` и только если включён
флаг «догрузить историю» (`settings.md`, вид 7). Строки, дописанные после
этого, и все строки файлов, появившихся позже, уходят с `backfill` =
`false`. Флаг, включённый позже, отправляет историю тогда же; признак
у строк всё равно `true`. Отсутствующий атрибут `backfill` сервер
понимает как `false`.

### Время

Поля `LogRecord` — `timeUnixNano` и `observedTimeUnixNano`, наносекунды
Unix-времени в UTC (fixed64; в JSON-кодировке OTLP — десятичная строка).

| Поле | Тип | Обязательность | Событие хука | Строка транскрипта (живая и история) |
|---|---|---|---|---|
| `timeUnixNano` (`Timestamp`) | fixed64 | да у хука; если есть у строки | момент, когда `hottell hook` дочитал stdin. В событиях хуков обоих агентов нет своего поля времени, это время события | время из поля `timestamp` верхнего уровня самой строки (ISO 8601; есть у записей Codex и у большинства записей Claude). Нет поля или оно не разбирается — `0` или поле не заполнено: время неизвестно, сервер понимает оба варианта одинаково |
| `observedTimeUnixNano` (`ObservedTimestamp`) | fixed64 | да | момент, когда фоновый процесс собрал запись для отправки из очереди хуков | момент, когда бинарь прочитал строку из файла |

- У истории `timeUnixNano` — исходное время записи, дни и месяцы назад,
  а `observedTimeUnixNano` — время догрузки. Разница двух полей показывает
  задержку доставки, по истории — её возраст.
- Сервер время не переписывает. Для записей с `timeUnixNano` = `0`
  отбор по времени идёт по `observedTimeUnixNano`.

## Приём

Приём OTLP работает в Go-сервисе на том же адресе, что и `/mcp`
(`<SERVICE_URL>` из [native-otel.md](native-otel.md), «Обозначения»).
Сервис проверяет токен коллектора, проставляет `hottell.user.id`
и передаёт данные в OTel Collector (HT-72, HT-74). Правила ниже одни
для бинаря (хуки, транскрипты, история) и для нативного OTel агентов.
Реакция на ответы описана только для бинаря: нативный OTel агенты
отправляют сами, и их реакцию бинарь не меняет.

### Endpoint и запрос

| Путь | Сигнал | Тело (`protobuf`) | Кто отправляет |
|---|---|---|---|
| `POST /v1/logs` | логи | `ExportLogsServiceRequest` | бинарь — все свои записи; нативный OTel обоих агентов — события |
| `POST /v1/metrics` | метрики | `ExportMetricsServiceRequest` | нативный OTel обоих агентов |
| `POST /v1/traces` | трейсы | `ExportTraceServiceRequest` | нативный OTel обоих агентов |

- **Транспорт** — только OTLP/HTTP. OTLP/gRPC приём не поддерживает.
  Метод — только `POST`, иначе `405`.
- **Токен** — заголовок `Authorization: Bearer <токен коллектора>`.
  Схема `Bearer` без учёта регистра, ровно один пробел перед токеном.
  Токен — тот, что бинарь получает через MCP (HT-54, HT-67); другие
  ключи (ключ MCP, сессия браузера) приём не принимает.
- **Кодировка тела** — заголовок `Content-Type`:

  | `Content-Type` | Кодировка |
  |---|---|
  | `application/x-protobuf` | двоичный protobuf (OTLP/HTTP binary) |
  | `application/json` | JSON-кодировка OTLP (OTLP/HTTP JSON) |

  Параметры после `;` (например, `charset=utf-8`) сервер не учитывает.
  Бинарь отправляет `application/x-protobuf`. JSON принимается для отладки
  и для клиентов, которые умеют только его; примеры в разделе «Записи»
  записаны в JSON для читаемости, по сети бинарь шлёт то же в protobuf.
  Нативный OTel обоих агентов настроен на protobuf
  ([native-otel.md](native-otel.md)).
- **Сжатие** — заголовок `Content-Encoding`: `gzip`, `identity` или
  без заголовка (без сжатия). Бинарь сжимает каждый запрос gzip.
- Ответ `2xx` — пустой `Export…ServiceResponse` в кодировке запроса.
  Поле `partial_success` сервер не заполняет: запрос принимается целиком
  или отвергается целиком.
- Тело ответа с ошибкой — `google.rpc.Status` в кодировке запроса;
  в ответах `405`, `401` и `415`, которые сервер даёт до разбора
  `Content-Type`, — в JSON. В `message` — текст причины
  в `message`. Бинарь на тело не опирается и показывает `message`
  в `hottell status`.

Сервер проверяет запрос в таком порядке и отвечает кодом первой
неудачной проверки: метод (`405`) → токен (`401`) → `Content-Type`
и `Content-Encoding` (`415`) → размер запроса (`413`) → разбор тела
(`400`) → размер одной записи (`413`) → передача в коллектор (`503`).
Токен проверяется до чтения тела, поэтому запрос без токена
не расходует приём. Если токен не удалось проверить (недоступно
хранилище ключей), ответ `503`, а не `401`: `401` означает только
«токена нет, он не распознан или отозван». Распаковка gzip идёт вместе
с чтением тела: битый gzip — `400`, а если распакованных данных больше
16 МиБ раньше, чем встретилась порча, — `413`.

### Лимиты

| Лимит | Значение | Что считается |
|---|---:|---|
| Запрос | **16 МиБ** = 16 777 216 байт | тело запроса после распаковки gzip; без сжатия — тело как есть |
| Одна запись | **8 МиБ** = 8 388 608 байт | размер одного элемента в protobuf-кодировке (`proto.Size`), независимо от кодировки запроса: `LogRecord` в `/v1/logs`, `Span` в `/v1/traces`, `Metric` в `/v1/metrics` |
| Пачка бинаря | **4 МиБ** = 4 194 304 байта | сумма размеров записей пачки в protobuf-кодировке до сжатия; соблюдает бинарь, сервер отдельно не проверяет |

- **Откуда числа.** Наибольшая наблюдённая запись — строка транскрипта
  Codex ≈ 2,4 МБ, расчётный потолок ≈ 3,2 МБ ([payload-sizes.md](payload-sizes.md),
  «Рекомендация для HT-57»). В protobuf запись занимает почти столько же,
  сколько исходная строка, поэтому 8 МиБ покрывают её с запасом больше
  чем вдвое. Запрос в 16 МиБ вмещает запись предельного размера
  в protobuf и обычную запись в JSON; JSON-запрос с одной записью около
  8 МиБ может превысить 16 МиБ из-за экранирования — такой клиент получит
  `413`. Бинарь шлёт protobuf, поэтому его это не касается.
- **Нативный OTel не измерялся.** Размеры событий нативного OTel в
  [payload-sizes.md](payload-sizes.md) не измерены, а лимиты содержимого
  агентов подняты до максимума ([native-otel.md](native-otel.md)).
  Событие больше 8 МиБ (например, `api_request_body` Claude с длинным
  контекстом) получит `413`, и агент потеряет весь запрос с этим
  событием: `partial_success` сервер не использует, а `413` SDK
  не повторяет. Контракт принимает этот риск; если такие потери
  появятся в данных, лимит записи пересматривается.
- **Коллектор принимает не меньше.** Приём передаёт в коллектор запросы
  до 16 МиБ, поэтому приёмник коллектора (HT-72) настроен принимать
  не меньше 16 МиБ на запрос: для OTLP/gRPC — `max_recv_msg_size_mib`,
  для OTLP/HTTP — `max_request_body_size`. Иначе отказ коллектора
  повторялся бы бесконечно (см. «Ответы сервера»).
- **Распаковку сервер ограничивает.** Сервер читает распакованное тело
  не дальше 16 777 216 байт; если данных больше, он отвечает `413`,
  не дочитывая и не распаковывая остальное. Сжатый запрос, который
  распаковывается больше чем в 16 МиБ, отвергается так же, как
  несжатый.
- **Пачки бинаря.** Бинарь собирает записи в пачку, пока сумма их
  размеров не превышает 4 МиБ. Запись больше 4 МиБ уходит отдельным
  запросом из одной записи. Так обычный запрос остаётся вчетверо ниже
  лимита, а повтор после сбоя не пересылает много лишнего.
- **Запись больше 8 МиБ** сервер не принимает даже отдельным запросом:
  ответ `413`. Бинарь не обрезает запись, чтобы уложиться в лимит
  (запись лежит целиком, раздел «Записи»). Он проверяет размер сам по
  тому же правилу (`proto.Size` записи) и такую запись не отправляет,
  а сразу переносит в папку отклонённых, как после `413`.
- Хук (`hottell hook`) лимитов не имеет: он читает stdin целиком, лимиты
  действуют только при отправке.

### Ответы сервера

| Ответ | Когда | Реакция бинаря |
|---|---|---|
| `2xx` | запрос принят и передан в коллектор | удалить отправленное из очереди |
| `400` | тело не разобрано: не protobuf или не JSON OTLP, битый gzip, не тот тип сообщения | пачка из нескольких записей — разбить на запросы по одной записи и отправить заново; запрос из одной записи — перенести запись в папку отклонённых, не повторять |
| `401` | нет заголовка `Authorization`, токен не распознан или отозван | остановить отправку, очередь не удалять, причину показать в `hottell status`; отправка возобновляется, когда бинарь получит через MCP другой токен коллектора |
| `413` | запрос больше 16 МиБ или в нём есть запись больше 8 МиБ | пачка из нескольких записей — разбить на запросы по одной записи и отправить заново; запрос из одной записи — запись не принимается даже отдельным запросом: перенести в папку отклонённых, не повторять, счётчик показать в `hottell status` |
| `429`, `503` и прочие `5xx` | приём или коллектор перегружен или недоступен | повтор того же запроса с нарастающей паузой |
| прочие `4xx` (`403`, `404`, `405`, `415` и т. д.) | запрос не туда или не того вида — ошибка настройки адреса или бинаря, а не записи | как `5xx`: повтор с нарастающей паузой, очередь не удалять, код показать в `hottell status` |
| нет ответа (сеть, TLS, тайм-аут 60 с) | — | как `5xx` |

- **Отказ всей пачки — не отказ записей.** После `400` или `413`
  бинарь разбивает пачку и отправляет записи по одной. Если отдельным
  запросом отвергнуты все записи пачки, дело не в записях, а в запросе
  или бинаре: бинарь возвращает их в очередь и действует как при
  прочих `4xx`. В папку отклонённых запись попадает, только когда
  она отвергнута отдельным запросом, а другие записи той же пачки
  приняты, или когда пачка и была из одной записи.
- **Коллектор.** Сервис отвечает `2xx`, только когда коллектор принял
  данные. Любой другой исход передачи (коллектор недоступен, ответил
  `4xx` или `5xx`) — ответ `503`: тело сервис уже разобрал сам, поэтому
  отказ коллектора — неполадка сервиса, а не записи, и запись
  не должна уйти в папку отклонённых.
- **Нарастающая пауза.** Первая пауза — 1 с, каждая следующая вдвое
  длиннее, не больше 5 минут, со случайным разбросом ±20 %. Если ответ
  `429` или `503` несёт заголовок `Retry-After` (секунды), пауза —
  не меньше этого значения, но не больше 5 минут. После любого `2xx` пауза сбрасывается к 1 с.
  Пока идёт повтор, новые записи ждут в очереди на диске.
- **Папка отклонённых** — локальный каталог бинаря; запись лежит там
  в том виде, в каком ушла, сервер её больше не получает.
  `hottell status` показывает число отклонённых записей отдельно
  для `400` и `413`.
- `401` не удаляет данные: записи ждут в очереди, пока токен не заменят.
- **Повторы.** Строку транскрипта сервер узнаёт по ключу строки
  и отбрасывает повтор (раздел «Строка транскрипта»). У события хука
  ключа нет: если сервер принял запрос, а ответ не дошёл до бинаря,
  повтор сохранит события хуков второй раз. Такие повторы допустимы.
