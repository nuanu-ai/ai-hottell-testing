# Локальные отчёты AI Hottell

Dashboard использует оформление из существующего [`demo/dashboard.html`](../demo/dashboard.html) — этот оригинал содержит только условные данные. Рабочий экран читает локальный ClickHouse и приватные файлы отчётов. Записанные события, восстановленная хронология и отсутствующие данные помечены отдельно. Он не меняет сборщик, настройки агентов или существующий Docker Compose. Адрес доступен только на этой машине: `http://127.0.0.1:8787`.

```sh
mkdir -p /Users/elvismusli/Life/projects/ai-hottell/local-data/bin
cd dashboard
go run . -data-dir ../local-data/reports
```

На странице каждой выбранной сессии доступны два отдельных визуальных отчёта: `/sessions/<session_id>/telemetry` и `/sessions/<session_id>/deep`. Общая матрица 13 проверок — `/coverage`. JSON: `/api/sessions`, `/api/reports/hooks/<session_id>`, `/api/reports/otel/<session_id>`, `/api/reports/delivery/<session_id>`, `/api/reports/telemetry/<session_id>`, `/api/reports/deep/<session_id>`, `/api/reports/coverage/<session_id>`. Список отделяет подготовленные отчёты от новых ID из Hooks и заявок по deep link.

## Версия 2.0 на локальном стенде

После сборки исполняемый файл можно хранить вне Git в `local-data/bin/`. Для работы с уже существующим приватным набором отчётов передавайте абсолютный путь к нему:

```sh
cd dashboard
go build -o /Users/elvismusli/Life/projects/ai-hottell/local-data/bin/hottell-dashboard-v2 .
/Users/elvismusli/Life/projects/ai-hottell/local-data/bin/hottell-dashboard-v2 -listen 127.0.0.1:8787 -data-dir /Users/elvismusli/Life/projects/ai-hottell/local-data/reports
```

В `local-data/reports/v2/deep/<session_id>.json` лежат Deep-отчёты 2.0 с отдельными заданиями, заявлениями «готово» и всеми 13 проверками. Общий реестр уже объединённых предложений — `local-data/reports/v2/proposals.json`. При наличии 2.0 дашборд показывает его первым; старый Deep JSON остаётся на месте. Технический отчёт по Hooks, нативному OTel и реконструкции продолжает жить отдельно. API нового формата: `/api/reports/deep-v2/<session_id>`, `/api/proposals`; `/api/reports/deep/<session_id>` отдаёт 2.0 при его наличии, иначе старый формат.

Нативный OTel запрашивается только по точному ID и в проверенном окне времени сессии. Локальное хранилище удерживает данные 30 дней; у старых сессий API показывает `coverage=partial` и точные границы проверенного окна. При неизвестном времени или сбое ClickHouse источник недоступен, а не равен нулю.

Техническая страница также читает локальный буфер сборщика по `-collector-config` (по умолчанию `~/.config/hottell/config.json`) и приватный диагностический файл внутри него. Она показывает ожидающие события, известные потери при переполнении и времена последней ошибки отправки и HTTP 2xx от коллектора. Ответ 2xx не доказывает запись в ClickHouse; старые ошибки и период до включения диагностики не восстанавливаются. Если буфер или диагностический файл недоступен, страница показывает это вместо нуля ошибок.

На странице «Сессии» можно вставить локальный deep link Codex или ID сессии. Кнопка «Разобрать новую сессию» создаёт только приватную заявку `local-data/reports/v2/requests/<session_id>.json` с правами `0600`; она не притворяется выполненным анализом. Для ссылки на удалённый чат без локального исходника обработчик честно сообщит о недоступном источнике. Локальный worker готовит отдельный технический кандидат из зафиксированного журнала и Deep-кандидат; записанные Hooks/OTel читаются из своих потоков. Worker запускается из корня этого checkout:

```sh
python3 local/v2_worker.py /Users/elvismusli/Life/projects/ai-hottell/local-data/reports --watch
```

Статус доступен на странице сессии и в `/api/analysis-requests/<session_id>`. Если обработка завершилась ошибкой, можно повторить её кнопкой: число попыток и последний код ошибки сохраняются. Worker создаёт только структурно проверенные кандидаты: для старой сессии Deep в `rebuild/<session_id>/deep.v2.json`, для новой Deep в `v2/review/<session_id>.json` и технический отчёт в `v2/review-telemetry/<session_id>/telemetry.json`. Статус `completed` до независимой смысловой проверки не равен опубликованному отчёту.

У опубликованной сессии кнопка повторного разбора появляется, только когда локальный журнал доступен. Worker фиксирует новый полный JSONL-префикс в `v2/review-sources/<session_id>.json`, оставляя опубликованную версию `v2/sources/<session_id>.json` на месте до проверки. Если SHA-256 источника не изменился, модель не вызывается и новое предложение не создаётся. При изменении источника Deep и технический отчёт снова проходят отдельную смысловую проверку. Агенту передаётся приватный журнал `v2/lifecycle/events.jsonl`: уже применённую ту же правку нельзя предлагать заново, а эффект требует отдельного доказательства.

Для новой сессии проверяющий агент читает исходные строки и отдельно проверяет границы задач, ранние заявления о готовности, все 13 пунктов, выбор предложений и отсутствие чувствительных данных. Он сохраняет приватный review JSON с `session_id`, SHA-256 **точного файла-кандидата**, `verdict: "approved"`, `reviewer`, `reviewed_at`, содержательным `note` и `checks: ["task_boundaries", "completion_claims", "all_13_checks", "proposal_choice", "sensitive_data"]`. Публикация после такой проверки:

```sh
python3 local/v2_publish_new.py /Users/elvismusli/Life/projects/ai-hottell/local-data/reports <session_id> /абсолютный/путь/к/private-review.json
```

Команда ещё раз сверяет зафиксированный источник, размещает Deep в `v2/deep/`, технический отчёт в `telemetry/`, обновляет версию источника и общий реестр. При ошибке опубликованные версии восстанавливаются из сохранённых байтов; прежние версии остаются в `v2/history/`. Файл проверки и отчёты остаются вне Git. Предложения не применяются кнопкой дашборда: готовность, решение владельца, применение и проверенный эффект показаны отдельно.

### Журнал жизненного цикла предложений

`local/v2_lifecycle.py` записывает **только подтверждённые метаданные** решения владельца, применения и проверки эффекта. Он не меняет настройки, файлы или права, которые предлагает карточка. Подготовьте приватный JSON-файл `0600` с полями `proposal_id`, `event`, `actor`, `authority_ref`, `detail` и вызовите:

```sh
python3 local/v2_lifecycle.py /абсолютный/путь/к/local-data/reports /абсолютный/путь/к/private-event.json
```

`proposal_id` берётся из опубликованного `v2/proposals.json`; `authority_ref` ссылается на реальное решение или проверку, без сырых диалогов и секретов. Для `event: "decision"` поле `detail` равно `{"status":"accepted"}` (либо `rejected` или `revision_requested`). Для `event: "application"` нужны `detail.version` новой версии, `target_version_verified` исходной версии из карточки, непустые `evidence[]`, `permission_ref` и `rule_review`; команда проверяет подготовленность и уже записанное принятие. Для `event: "effect"` нужны `status`, `method`, `metric`, `n_before`, `n_after`, `note`, непустые `evidence[]`; результат `helped`/`no_effect`/`worse` требует наблюдений до и после, а `insufficient_data` — объяснения в `note`. Эффект до применения отклоняется.

Приватная история хранится в `v2/lifecycle/events.jsonl` (`0600`) с цепочкой хэшей. Каждая запись содержит `schema_version: 1`, `event_id`, `recorded_at`, `proposal_id`, `proposal_fingerprint`, `event`, `actor`, `authority_ref`, копию `proposal_sources`, `detail`, `previous_hash`, `record_hash`. Fingerprint привязывает запись к `group_key`, `target` и `change`; новая версия цели или правки требует нового решения. Реестр пересобирается после записи и при следующем обновлении Deep; прежние применения остаются в журнале. Если обновление реестра после записи не удалось, команда сообщает об этом: запись уже сохранена, повторите `local/v2_registry.py <reports> --published`.

## Два вида отчёта

1. **Технический** показывает три источника раздельно: ретроспективный отчёт `local-data/reports/telemetry/<session_id>.json`, записанные Hooks из `otel.otel_logs` с `ServiceName = 'agent-hooks'` и OTel logs/traces/metric records, связанные с сессией по точному `session_id` или `conversation.id`. Он показывает время записи. События, извлечённые из локального транскрипта старой сессии, имеют `source: "transcript"` и `provenance: "reconstructed"`; они не считаются записанными Hooks или OTel. Глобальные метрики и трейсы без ID сессии не распределяются по отчётам. Неизвестные стоимость, задержка, качество и экономия времени не оцениваются.
2. **Deep** создаётся отдельно аналитическим агентом после чтения полной выбранной сессии из предоставленного человеком deep link и локального журнала. Dashboard сам не запускает модель. Агент сохраняет один JSON на сессию в `local-data/reports/deep/<session_id>.json`. Обе папки исключены из Git. Сессия без записанных хуков всё равно может иметь технический ретроспективный и глубокий отчёты.

Формат deep:

```json
{
  "kind": "deep",
  "session_id": "example-session",
  "task": "Что человек пытался получить",
  "outcome": "unknown",
  "outcome_basis": "Нет проверки результата или подтверждения человека",
  "model_opinion": "unknown",
  "observations": [],
  "recommendations": [],
  "unknowns": ["Что считалось готовым?"]
}
```

`outcome`: `verified`, `partial`, `failed`, `unknown`. Мнение модели указывается отдельно и само по себе не подтверждает результат. Каждое наблюдение содержит `pattern`, `finding`, `status` (`suspected`, `confirmed`, `dismissed`) и непустой `evidence` со ссылками на шаги сессии. Рекомендация содержит `action`, `target`, `change`, `status: "draft"` и непустой `evidence`. Dashboard только показывает черновик; применение изменений остаётся отдельным решением человека. Не копируйте в отчёт секреты, сырые диалоги и клиентские данные.

## Полное покрытие концепта

По запросу Александра от 30.09.2026 для каждой выбранной сессии учитываются **все 13** пунктов каталога v0.1. Ограничение пилотной инструкции до D03, D05 и D10 для этого прогона отменено. Статус каждого пункта показывает фактическую глубину проверки; наличие строки в матрице само по себе не означает завершённый анализ. Источник правил — ветка `docs/analysis-concept-2026-09-29` (`analytics/catalogue.yaml`, `analytics/criteria.md`, `analytics/model.md`). Это агентный разбор доступного корпуса, а не реализация автоматических детекторов.

Каждый пункт получает один из пяти статусов: `suspected` (есть сигнал, ждёт человеческого подтверждения), `checked_clear` (нужные данные просмотрены, сигнал не найден), `insufficient_data` (требуемого входа действительно нет), `not_checked` (вход доступен, но разбор ещё не завершён) или `not_applicable` (условие не относится к сессии). Если отчёта нет, дашборд также показывает «не проверено». Отсутствие находки само по себе не превращается в `checked_clear`. Отсутствие подготовленного извлечения не означает `insufficient_data`, когда исходные записи доступны.

Приватные результаты лежат в `local-data/reports/coverage/<session_id>.json`, по одному файлу на сессию, и не попадают в Git. Отдельные агенты разбирают локальные и межсессионные проверки; `python3 dashboard/merge_coverage.py /абсолютный/путь/к/local-data/reports` проверяет наличие всех 13 пунктов, связывает их с исходным SHA и собирает полные файлы. Deep-страница показывает список со статусом, основанием и недостающими данными; страница выводов показывает сигналы повторного разбора рядом с прежними Deep-наблюдениями. Технические выводы из Hooks/OTel остаются отдельно; восстановленный транскрипт не объявляется записанной телеметрией. Ни один сигнал не считается подтверждённой ошибкой без проверки человеком.

## Повторная сборка приватных отчётов

Список выбранных сессий, число доступных строк и SHA исходного среза зафиксированы в `local-data/reports/telemetry/manifest.json`. `rebuild_telemetry.py` пересчитывает только события и счётчики из этих срезов в `local-data/reports/rebuild/<session_id>/telemetry.json`; он не подменяет ими исторические Hooks или OTel. Поля токенов используют последний накопительный счётчик каждого наблюдаемого сегмента, а не сумму повторных снимков, и не означают оплаченный расход. Поле `user_messages` считает записи с ролью `user`, включая служебные вставки.

Отдельный аналитический агент готовит `deep.json`, `coverage.json` и `technical_notes.json` для каждой сессии в том же приватном каталоге. После резервной копии текущих отчётов `promote_rebuild.py` проверяет все сессии, схемы, локальные ссылки на строки и границу исходного среза. Без `--promote` он только проверяет; с этим параметром заменяет три опубликованных локально JSON для каждой сессии. Исходные журналы и приватные отчёты не добавляются в Git.
