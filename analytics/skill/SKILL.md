# session-retro

Для AI Hottell 2.0 используй [протокол заданий и 13 проверок](../v2_analysis.md) и `../v2_contract.py`. Описанный ниже `schemas.json` — прежний формат; он не содержит границ заданий и всех ранних заявлений о завершении. Не публикуй его выводы как Deep 2.0.

Глубоко разбираешь завершённую сессию человека с агентом Codex или Claude Code — целиком, по его запросу, в отдельной аналитической сессии — и возвращаешь результат строго по схемам [schemas.json](schemas.json). Ходы уже прошли быстрый разбор ([../quick-review.md](../quick-review.md)): классы реплик и отметки хода готовы. Правила детекторов — [../catalogue.yaml](../catalogue.yaml), поля — [../model.md](../model.md), вердикт и метрики — [../metrics.md](../metrics.md), критерии — [../criteria.md](../criteria.md).

## Границы

- Сам ничего не меняешь: ни файлы проекта, ни настройки, ни инструкции. Изменения — черновики в `proposals`. Применяешь рекомендацию только по команде человека («примени рекомендацию …» или кнопка «Применить»): показываешь точное изменение — diff, текст правила, черновик skill, — вносишь после подтверждения и отмечаешь внедрённым.
- Эта сессия — аналитическая: её саму не разбираешь.
- Работаешь с данными через MCP проекта, а до его появления — запросами `SELECT` к ClickHouse (ниже); с настройками на этой машине — только чтение.
- Не переносишь в выход секреты, ключи, токены, пароли, номера карт и счетов, личные данные третьих лиц; в цитатах заменяешь их на `[скрыто]`.
- Каждое утверждение об эпизоде или результате ссылается на evidence: `call_id`, `turn_index`, `event_id`. Нет evidence — нет утверждения.
- Недостаточно данных — пишешь `unknown` и задаёшь вопрос, а не угадываешь.
- Отвечаешь человеку на его языке, коротко.

## Какие данные нужны

Как их отдавать (MCP проекта), решает и делает техническая часть, включая названия инструментов. Skill нужно:

1. найти сессии: последнюю, по id, за период, по участнику;
2. получить сводку сессии: постановка и реплики человека, ходы агента с финальными сообщениями, компакции, разрешения, использование skills, вердикт по проверкам, эпизоды `suspected`, результаты быстрого разбора ходов (`turn_review`);
3. искать по сессии — вызовы по инструменту, успеху или тексту ошибки — и открывать вызов или ход по id с вводом и выводом (выводы до 2 KB). Сессию целиком не загружаешь: открываешь те места, которые нужны для решения;
4. получить инструкции человека из его сессий за 30 дней — для D10;
5. получить сессии того же класса с их затратами и использованием skills — для D19 и D25;
6. получить примеры из разметки человека — см. ниже;
7. записать: `episode_reviews`, `human_turns`, новые эпизоды, `facets`, `verdict_opinion`, `orange_flag`, `config_review`, `proposals`, `other_findings`, разметку человека.

## Локальные сессии: полный аудит каталога

Хранилища результатов ещё нет, но MCP `hottell` уже читает локальные сессии обоих агентов. Этого достаточно:

| Нужно | Чем сейчас |
|---|---|
| 1. найти сессии | `sessions_list` — агент, период, проект |
| 2. сводка сессии | `session_stats` по сессии и `session_read` с видами `user_message`, `assistant_message`, `compact`, `turn_start/end` |
| 3. поиск и открытие мест | `session_read` с видами `tool_call`, `tool_result`, постранично, с обрезкой текстов |
| 4. инструкции за 30 дней | `sessions_list` за период + `session_read` с видом `user_message` |
| 5. сессии того же класса | классы из прошлых разборов в `local-data/retro/` |
| 6. примеры из разметки | `local-data/labels.jsonl` |
| 7. запись | JSON по схемам в `local-data/retro/<session_id>.json`, разметка — строкой в `local-data/labels.jsonl` |

Быстрого разбора в локальном режиме нет — классы реплик ставишь сам (шаг 2). Вердикт по проверкам считаешь сам по [criteria.md](../criteria.md) и помечаешь `by: skill`; разметка человека главнее. Для каждой выбранной сессии **обязательно оцени все 13 пунктов** каталога: D01, D03, D05, D07, D10, D12, D13, D16, D19, D22, D24, D25, D26. Не ограничивайся D03/D05/D10. Структурный слой, который ещё не реализован автоматически, проверяй по доступным исходным записям; не называй ручную проверку автоматическим детектором.

В `detector_checks` пиши один пункт на каждый ID в порядке каталога: `suspected` (сигнал с доказательством, ждёт проверки человеком), `checked_clear` (нужные данные просмотрены, сигнал не найден), `insufficient_data` (перечисли недостающие входы) либо `not_applicable` (объясни, почему условие не относится к сессии). Пустой список эпизодов не означает `checked_clear`. Для межсессионных D10, D13, D19, D22, D25, D26 соблюдай окна, пороги и исключения каталога; если нет сравнимых задач, подтверждённого исхода, истории использования skill или инвентаря конфигурации на дату сессии, пиши `insufficient_data`, а не «проблемы нет». Токены из повторных накопительных снимков не суммируй.

Запасной путь — `SELECT` к ClickHouse пользователем `reader` по [../model.md §4](../model.md#4-где-это-в-clickhouse); пароль не выводишь и не сохраняешь в файлы. Если нет ни MCP, ни доступа — скажи об этом человеку и остановись.

## Примеры из разметки

Перед разбором возьми из разметки человека: по каждому детектору до 5 последних эпизодов, которые он подтвердил или снял (снятых — не меньше трети), и реплики, класс которых он исправил. Это образец того, как он решает. Похожий случай решай так же; решение человека главнее твоего.

## Порядок

### 1. Сессия

По запросу: `last` — последняя завершённая сессия участника; id — указанная; период — по очереди все сессии периода, затем сводка по паттернам.

### 2. Реплики человека → `human_turns`

Классы уже поставил быстрый разбор. Перепроверь реплики с `confidence` ниже 0.6 и реплики без разбора (быстрый разбор отключён или не сработал); остальные бери как есть. В `human_turns` пиши только исправленные и новые.

Первая реплика — постановка. Классы следующих:

- `correction` — агент неверно понял то, что уже было доступно: в постановке, файлах, прошлых репликах. Признак: человек возвращает агента к уже известному («я же писал», «нет, только…», «не тот файл»).
- `clarification` — человек добавляет данные, которых в постановке не было.
- `answer` — ответ на вопрос агента из предыдущего хода.
- `goal_change` — человек увидел результат и хочет другое.
- `new_task` — новая задача в той же сессии.
- `ack` — «да», «ок», «продолжай» без новых данных.

Если по тексту не отличить `correction` от `clarification`, проверь постановку: данные там были → `correction`.

### 3. Эпизоды `suspected` → `episode_reviews`

Для каждого эпизода от ядра проверь исключения детектора из каталога. `confirm` — если сигнал есть и ни одно исключение не подходит; `dismiss` — если подходит исключение, назови его; `known` — если это уже известная человеку проблема из открытого предложения. Решение человека главнее твоего.

### 4. Смысловые детекторы → новые эпизоды со статусом `suspected`

D01 и D05 считает ядро по результатам быстрого разбора. Если их нет — определи сам:

- **D12** — агент переспрашивает то, на что человек уже ответил, или нарушает его указание из этой же сессии. Открой исходную реплику и место повтора; эпизод со ссылками на оба.
- **D01** — по классам реплик: `correction` или `clarification` среди первых трёх реплик после постановки. Отметь, есть ли в постановке критерий готовности.
- **D05** — проверь каждое существенное заявление о завершении внутри каждого задания в момент, когда оно было сделано, включая раннее «готово», позже исправленное. Сопоставь заявленный объём с доступным тогда подтверждением; честное «черновик готов, проверь» не выдаёт всю задачу за завершённую.
- **D10** — императив о способе работы («сначала…», «всегда…», «не трогай…») совпадает по смыслу с инструкцией из других сессий за 30 дней. Инструкции о содержании задачи — суммы, даты, файлы — не считаются.
- **D19** — прочитай на этой машине установленные skills и их `description`; если skill подходит задаче сессии, но не использовался, — эпизод с затратами относительно сессий класса, где он использовался.
- **D25** — после использования skill есть подтверждённые эпизоды или вердикт `partial` / `failed`, и так было в другой сессии с этим skill.
- **D26** — прочитай на этой машине настройки: глобальные и проектные AGENTS.md, CLAUDE.md, память, skills, конфигурацию MCP. Для каждого элемента — дата изменения и хэш; для инструкций — список правил. Отметь `stale` (не менялся дольше 60 дней, а после изменения в сессиях появилась новая модель), `unused` (skill или MCP не использовался 30 дней), `contradicted` (правило противоречит репликам человека или человек его повторяет). Содержимое файлов в выход не переноси — только вид пути, даты, номера правил и короткое описание.

- **Другое** — проблема, которой нет в каталоге: одна строка в `other_findings` со ссылками на шаги. Эпизод не создаёшь.

### 4а. Полное покрытие → `detector_checks`

После проверки сигналов и исключений заполни статус **каждого** из 13 детекторов. D03, D07, D13, D16, D22 и D24 проверяй по их структурным условиям, D01 и D05 — по репликам и проверкам результата, D10, D12, D19, D25 и D26 — по смысловым и межсессионным входам. Для `suspected` и `checked_clear` укажи просмотренные вызовы, реплики или диапазон источника; для `insufficient_data` назови конкретно недостающий вход. Не переноси сюда подробный текст сырых сессий и настройки с секретами. Сигнал в этой таблице не равен подтверждённой ошибке и сам по себе не запускает изменение системы.

### 5. Фасеты → `facets`

`goal_category` по [criteria.md](../criteria.md); задача одной фразой; критерий готовности — из постановки, иначе из шаблона класса с пометкой `proposed`; где ушло время — участки ходов с причиной; кандидаты в автоматизацию — повторяющиеся последовательности шагов.

### 6. Результат → `verdict_opinion` и `orange_flag`

Оцени по пунктам критерия, выполнен ли каждый, со ссылкой на evidence. Это мнение модели: вердикт не меняешь. Если вердикт `unknown` — сформулируй вопросы оранжевого флага:

1. «Какая была цель этой сессии — одной фразой?»
2. «Что должно было получиться, чтобы считать задачу сделанной? 2–3 пункта.»
3. «Результат принят как есть, с доработкой или не сделан?»

Задавай только те, ответа на которые нет.

### 7. Черновики изменений → `proposals`

Предлагаешь уже по одной сессии. Для каждого паттерна с подтверждённым эпизодом в разбираемой сессии (подтвердил ты на шаге 3 или человек):

- паттерн подтверждён только здесь → `basis: single_session`, `confidence` не выше 0.6, приоритет по затратам эпизода;
- подтверждённые эпизоды того же паттерна есть в других сессиях → `basis: repeated`, `sessions_count` — их число, уверенность и приоритет выше;
- на паттерн уже есть открытое предложение → новое не создаёшь, называешь его и добавляешь evidence.

Без подтверждённого эпизода предложения нет — только наблюдение.

Шесть частей: паттерн, evidence, гипотеза причины, «что было — что должно быть» с классом действия и адресом, ожидаемый эффект с метрикой проверки, приоритет и уверенность. Классы: `policy` — одна строка с условием срабатывания; `skill` — что изменить в шагах или description; `settings` — что обновить или удалить; `hook` — событие, условие, текст подсказки агенту (сначала подсказка, блокировка — только после проверки); `script` — вход, выход, шаги, где нужна модель; `human` — кто, когда, что делает.

Перед черновиком найди в настройках похожее правило. Правило есть, но не выполняется — предлагай `hook` или `settings`, а не повтор текста.

Убрать skill или правило — осторожно. Укажи шаг, на котором оно сбилось, и в `alternative_cause` — другое возможное объяснение (skill применяли к самым трудным случаям; правило нужно редко, но нужно). По умолчанию предлагай исправить шаг или сузить, когда skill срабатывает. Удаление — только если skill не помог ни в одной сессии класса за период.

### 8. Карточка человеку

```
Сессия: <задача одной фразой> · <агент> · <длительность>
Результат: <вердикт> — <на чём основан>; мнение модели: <…>
Где ушло время: <эпизод> — <затраты>; <эпизод> — <затраты>
Подтвердите: 1) <эпизод> — верно / шум   2) …
Вопросы: <оранжевый флаг, если есть>
Предложение: <было → должно быть> · <по одной сессии / повтор в N сессиях> — принять / отклонить / изменить
Разметка: задача (к какой относится) · критерий готовности · результат 0–3 · доработка, мин · в командный срез: нет / метрики / метрики и фасеты / с цитатами
```

Ответы человека запиши как разметку и `Review` с `by: human`.
